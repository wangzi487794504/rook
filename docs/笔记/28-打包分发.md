# 28 — 打包分发：免装 Java 的绿色产物

## 这一章做什么

把 Rook 从「源码 + Maven」变成「解压即用的绿色目录」——目标用户**不用预装 Java**，双击一个可执行文件就能跑。同时记录打包过程中踩过并修掉的六个坑（乱码、资源丢失、闪退、进程占用、搜索解析 bug、搜索 key 配置）。

**读完这一章你能做到：**

- 用 `maven-shade-plugin` 打出自包含的 fat jar（`java -jar` 直接能跑）
- 用 `jlink` 裁剪出最小 JRE（不含 `javac`，体积可控）
- 用 `jpackage` 生成自带运行时的 app-image（绿色目录）
- 写一套 Windows / macOS / Linux 三平台打包脚本，一键产出 zip / tar.gz
- 理解并复现六个「打包后才发现」的改造点

## 为什么需要

### 目标用户不该被要求装 Java

Rook 是终端 AI 助手，理想形态是「下载 → 解压 → 双击 → 用」。如果要求用户先装 JDK 17、配环境变量，门槛太高。

**目标**：产出自带裁剪运行时的绿色目录，未装 Java 的机器也能启动。

### 瘦 JAR 跑不起来

一开始 `pom.xml` 只配了 `maven-jar-plugin`，打出来的是**瘦 JAR**——只有 Rook 自己的 class，依赖（Jackson、JLine、SnakeYAML…）都没打进去。直接 `java -jar` 会报：

```
ClassNotFoundException: com.fasterxml.jackson.databind.ObjectMapper
```

瘦 JAR 只能配合 Maven 的 classpath 用，无法独立分发。

### 三种产物形态

| 产物 | 载体 | 用途 |
| :--- | :--- | :--- |
| fat jar | `target/rook-0.1.0-SNAPSHOT.jar` | 装了 Java 的机器 `java -jar` 直接跑 |
| app-image | `dist/rook/`（含 `rook.exe` / `rook` + `runtime/`） | 免装 Java，绿色目录 |
| 归档 | `dist/rook-0.1.0-SNAPSHOT-win.zip` / `-mac.tar.gz` / `-linux.tar.gz` | 分发单文件 |

## 打包流程总览

构建链分三个阶段，一个组件对应一层：

```
源码 ──(1) Maven Shade──▶ fat jar ──(2) jlink + jpackage──▶ 绿色目录 ──(3) 归档──▶ zip/tar.gz
```

| 阶段 | 工具 | 产出 |
| :--- | :--- | :--- |
| ① 打 fat jar | `maven-shade-plugin` | 依赖 + 入口 + services 合并进一个 jar |
| ② 生成绿色目录 | `jlink`（裁剪 JRE）+ `jpackage`（封装 app-image） | `dist/rook/`，内含 `runtime/` |
| ③ 归档 | `tar`（Windows 用 `tar -a`，Unix 用 `tar -czf`） | 单文件 zip / tar.gz |

## 核心概念

### fat jar 是什么

把**项目字节码 + 所有运行时依赖**塞进同一个 JAR，并写入 `Main-Class`，让 `java -jar` 一条命令就能启动，不再依赖外部 classpath。

关键点不是「能打出来」，而是**合并正确**：

- **`ManifestResourceTransformer`** —— 覆盖依赖里自带的 `META-INF/MANIFEST.MF`，写入正确的 `Main-Class`
- **`ServicesResourceTransformer`** —— 合并 `META-INF/services`（JLine 等库用 SPI 加载实现类），否则会被「覆盖」而不是「合并」，运行时找不到实现
- **排除签名文件** —— 依赖 jar 里的 `META-INF/*.SF / *.DSA / *.RSA` 校验不通过会报 `Invalid signature file digest`

### jlink 与裁剪 JRE

`jlink` 从完整 JDK 里拼一个**只含指定模块**的最小运行时。模块列表由 `jdeps` 分析依赖得出：

```
jlink --add-modules java.base,java.desktop,java.management,java.net.http,java.sql,jdk.crypto.ec \
      --strip-debug --no-header-files --no-man-pages \
      --output dist/jre
```

几个容易漏的点：

- **`jdk.crypto.ec`** —— HTTPS 需要椭圆曲线加密，通过 `ServiceLoader` 动态加载，`jdeps` 静态分析抓不到，必须手动加
- **`--strip-debug --no-header-files --no-man-pages`** —— 去掉调试符号、头文件、手册，进一步压缩体积
- 裁剪后的 JRE 里**没有 `javac`**，这正好是「裁剪干净」的标志

### jpackage 与 app-image

`jpackage` 把 fat jar + 裁剪 JRE 封装成**平台原生的可执行目录**：

```
jpackage --type app-image --name rook \
         --input dist/input \
         --main-jar rook-0.1.0-SNAPSHOT.jar \
         --main-class com.rook.cli.Main \
         --dest dist \
         --win-console \
         --runtime-image dist/jre
```

- `--type app-image` —— 生成绿色目录（不是安装器 `.msi` / `.dmg`）
- `--win-console` —— **Windows 专用**，走控制台子系统，CLI 工具必须加，否则双击无输出
- `--runtime-image` —— 用前面 `jlink` 裁好的 JRE，而不是 jpackage 自己临时裁一个

产物结构：

```
dist/rook/
├── rook.exe / rook        # 启动器
├── app/                   # fat jar 及依赖
└── runtime/               # 裁剪 JRE
```

### 三平台差异

| 平台 | 脚本 | 启动器 | 归档命令 | 特殊参数 |
| :--- | :--- | :--- | :--- | :--- |
| Windows | `package.bat` | `rook.exe` | `tar -a -c -f ...win.zip` | `--win-console` |
| macOS | `package.sh` | `rook` | `tar -czf ...mac.tar.gz` | 无 |
| Linux | `package.sh` | `rook` | `tar -czf ...linux.tar.gz` | 无 |

`package.sh` 用 `uname -s` 判断 `Darwin`（mac）还是其他（linux），一套脚本覆盖两个平台。

## 第一步：打 fat jar（maven-shade-plugin）

在 `pom.xml` 的 `<build><plugins>` 里加 shade 插件，绑定 `package` 阶段：

```xml
<plugin>
    <groupId>org.apache.maven.plugins</groupId>
    <artifactId>maven-shade-plugin</artifactId>
    <version>3.6.0</version>
    <executions>
        <execution>
            <phase>package</phase>
            <goals><goal>shade</goal></goals>
            <configuration>
                <createDependencyReducedPom>false</createDependencyReducedPom>
                <transformers>
                    <transformer implementation="org.apache.maven.plugins.shade.resource.ManifestResourceTransformer">
                        <mainClass>com.rook.cli.Main</mainClass>
                    </transformer>
                    <transformer implementation="org.apache.maven.plugins.shade.resource.ServicesResourceTransformer"/>
                </transformers>
                <filters>
                    <filter>
                        <artifact>*:*</artifact>
                        <excludes>
                            <exclude>META-INF/*.SF</exclude>
                            <exclude>META-INF/*.DSA</exclude>
                            <exclude>META-INF/*.RSA</exclude>
                        </excludes>
                    </filter>
                </filters>
            </configuration>
        </execution>
    </executions>
</plugin>
```

**三个 transformer 的作用**：

| transformer | 作用 | 少了会怎样 |
| :--- | :--- | :--- |
| `ManifestResourceTransformer` | 写入正确的 `Main-Class` | `java -jar` 报「no main manifest attribute」 |
| `ServicesResourceTransformer` | 合并 `META-INF/services` | JLine 等 SPI 库加载不到实现类 |
| （无 transformer，靠 filter） | 排除签名文件 | 启动报 `Invalid signature file digest` |

**验证**：

```bash
./mvnw clean package
java -jar target/rook-0.1.0-SNAPSHOT.jar
```

能启动 REPL、无 `ClassNotFoundException` 即成功。

## 第二步：裁剪最小 JRE（jlink）

```bash
jlink --add-modules java.base,java.desktop,java.management,java.net.http,java.sql,jdk.crypto.ec \
      --strip-debug --no-header-files --no-man-pages \
      --output dist/jre
```

**模块列表从哪来**：先用 `jdeps` 分析 fat jar 的依赖：

```bash
jdeps --print-module-deps --ignore-missing-deps target/rook-0.1.0-SNAPSHOT.jar
```

结果基础上**手动补 `jdk.crypto.ec`**（HTTPS 的椭圆曲线加密走 ServiceLoader，静态分析抓不到）。

## 第三步：生成 app-image（jpackage）

```bash
jpackage --type app-image --name rook \
         --input dist/input \
         --main-jar rook-0.1.0-SNAPSHOT.jar \
         --main-class com.rook.cli.Main \
         --dest dist \
         --win-console \
         --runtime-image dist/jre
```

**注意 `--input` 要指向一个「只有 fat jar」的干净目录**：jpackage 会把整个 `--input` 目录拷进 `app/`，如果直接指 `target/`，会把 Maven 的一堆中间产物（`classes/`、`test-classes/`、`maven-status/`…）都带进去。所以脚本里先：

```bash
mkdir dist\input
copy /y target\rook-0.1.0-SNAPSHOT.jar dist\input\
```

## 第四步：归档

Windows：

```bash
tar -a -c -f dist\rook-0.1.0-SNAPSHOT-win.zip -C dist rook
```

macOS / Linux：

```bash
tar -czf dist/rook-0.1.0-SNAPSHOT-${SUFFIX}.tar.gz -C dist rook
```

零额外工具（对应「不依赖 WiX / 签名 / 公证」的目标）。

## 第五步：脚本串联

`scripts/package.bat`（Windows）完整流程：

```bat
:: 1. 打 fat jar
call .\mvnw.cmd clean package

:: 2. 清理旧产物（先杀进程，见「改造四」）
taskkill /F /IM rook.exe >nul 2>&1
if exist dist rmdir /s /q dist
mkdir dist

:: 3. 干净输入目录
mkdir dist\input
copy /y target\rook-0.1.0-SNAPSHOT.jar dist\input\

:: 4. jlink 裁剪 JRE
jlink --add-modules ... --output dist\jre

:: 5. jpackage 生成 app-image
jpackage --type app-image ... --runtime-image dist\jre

:: 6. 清理中间目录
rmdir /s /q dist\input
rmdir /s /q dist\jre

:: 6a. 附带 config.yaml（见「改造三」）
copy /y config.yaml dist\rook\

:: 6b. 附带项目配置 .rook/（MCP / Hook / rules）
if exist .rook xcopy /e /i /y .rook dist\rook\.rook

:: 7. 归档
tar -a -c -f dist\rook-0.1.0-SNAPSHOT-win.zip -C dist rook
```

`package.sh` 结构相同，只是 `taskkill` 换成 `rm -rf dist`（Unix 没有进程占用问题），归档换 `tar -czf`，`uname` 判断平台后缀。

## 改造一：中文乱码 —— 统一走 JLine 输出

### 现象

打包后在 Windows 双击 `rook.exe`，启动日志里的中文全变成乱码（`姝ｅ湪鍔犺浇閰嶇疆` 这种）。

### 根因

两条输出路径编码不一致：

- **`System.out.println`** —— 字节流，走 Windows 控制台代码页。Java 17 在中文 Windows 上默认 GBK（CP936），而 Git Bash 是 UTF-8，两边对不上就乱码
- **JLine 的 `terminal.writer()`** —— 在 Windows 上直写控制台（`WriteConsoleW`，Unicode），**绕开字节编码/代码页问题**

之前只在 Git Bash 里测，没暴露；一换 Windows 控制台就露馅。

### 改法

`Main.java` 启动时创建 JLine 终端，并把 `System.out / System.err` 重定向到终端的输出通道：

```java
Terminal terminal = null;
try {
    terminal = TerminalBuilder.builder()
            .encoding(StandardCharsets.UTF_8)
            .build();
    PrintStream out = new PrintStream(terminal.output(), true, terminal.encoding());
    System.setOut(out);
    System.setErr(out);
} catch (Exception ignored) {
    // 无控制台环境时保持默认输出，不阻塞启动
}
new App().run(Paths.get(configPath), terminal);
```

**关键点**：

1. `.encoding(UTF_8)` —— 让 JLine 自己按 UTF-8 解码，Git Bash 的 dumb-terminal 回退也正确
2. `System.setOut(terminal.output())` —— 全局所有 `System.out.println` 都走 JLine 直写，一处改、处处生效
3. 终端对象传进 `App` / `Repl` 复用，不重复创建

改完后，开发（`mvn exec:java`）和打包（双击 exe）用同一套输出，两边中文都正常。

## 改造二：内置资源随包分发 —— classpath 加载

### 现象

打包后启动，日志显示 `[Skill] 已加载 0 个 Skill`，MCP 也没了——内置 Skill / SubAgent 全部丢失。

### 根因

内置 Skill / SubAgent 之前是从**源码路径**加载的：

```java
// 旧写法：直接指 src 目录，打包后根本不存在
Path builtinSkills = Path.of("src/main/java/com/rook/skills/builtin");
```

`src/` 在 fat jar 里不存在，所以打包后加载 0 个。

### 改法

改成**从 classpath 加载**，开发（`file:` URL）和打包（`jar:` URL）走同一套代码：

**① pom.xml 把内置 `.md` 打包进 jar**：

```xml
<resources>
    <resource><directory>src/main/resources</directory></resource>
    <resource>
        <directory>src/main/java</directory>
        <includes><include>**/*.md</include></includes>
    </resource>
</resources>
```

`mvn compile` 时 `src/main/java/**/*.md` 会被复制到 `target/classes`，于是开发模式 classpath 里也有。

**② 新增 `ClasspathScanner`**，统一处理两种 URL：

- `jar:file:...!/com/rook/skills/builtin` —— 用 `JarURLConnection` 枚举 jar 内子目录
- `file:.../target/classes/com/rook/skills/builtin` —— 用 `Files.list` 枚举目录

**③ `SkillLoader.loadAll` / `AgentDefLoader.loadAll` 去掉 `builtinDir` 参数**，改为内部调 `loadBuiltin()` 从 classpath 读，再和用户目录、项目目录做三级合并（项目 > 用户 > 内置）。

改造后开发与打包完全一致：内置 3 个 Skill、3 个 SubAgent、`.rook/` 里的 MCP 配置都能正常加载。

## 改造三：双击闪退 —— config.yaml 缺失

### 现象

双击 `dist\rook\rook.exe` 直接闪退（窗口一闪而过）。

### 根因

`dist\rook\` 里**没有 `config.yaml`**，`ConfigLoader.load` 抛异常 → `System.exit(1)` → 控制台窗口立刻关闭。

### 改法

打包脚本里把 `config.yaml` 连同 `.rook/` 一起拷进 app-image：

```bat
:: 6a. 附带 config.yaml
copy /y config.yaml dist\rook\

:: 6b. 附带项目配置 .rook/（MCP / Hook / rules）
if exist .rook xcopy /e /i /y .rook dist\rook\.rook
```

**注意**：`config.yaml` 里的 `api_key` 用 `${DEEPSEEK_API_KEY}` 环境变量占位符，**不写真实 key**（避免提交进 git）。运行时靠环境变量展开；想明文也可以，但别进 git。

## 改造四：进程占用 —— taskkill 守卫

### 现象

第二次打包时报错：`目标应用程序目录 D:\myclaude\dist\rook 已存在`，前面还有一串 `dist\rook\runtime\bin\*.dll - 拒绝访问`。

### 根因

`rmdir /s /q dist` 删不掉，因为**上一个 `rook.exe` 还开着**。它启动的 `java.exe` 子进程锁着 `runtime/` 里的 dll，Windows 上文件被占用就无法删除。

### 改法

删除前先杀进程：

```bat
taskkill /F /IM rook.exe >nul 2>&1
if exist dist rmdir /s /q dist
```

**但只杀 `rook.exe` 不够**：jpackage 的 launcher 会拉起 `runtime\bin\java.exe` 子进程，`rook.exe` 退了 `java.exe` 可能还在锁 dll。最稳妥的做法是**打包前先手动关掉正在运行的 Rook 窗口**，再跑脚本；否则即使 `taskkill` 掉了 launcher，`java.exe` 的 dll 句柄还在，照样删不掉。

> 排查技巧：`tasklist | findstr /i "java rook"` 看有没有残留进程；确认没有后 `rmdir /s /q dist` 能成功，再重打包。

## 改造五：搜索 HTML 解析 bug —— 兼容带属性标签

### 现象

`web_search` 每次都返回「未找到结果」，实际 curl 抓 Bing 明明有 10 条结果。

### 根因

Bing 的结果项标题标签是 **`<h2 class="">`（带 `class` 属性）**，而旧代码硬编码查找字面量 `<h2>`：

```java
// 旧写法：indexOf("<h2>") 匹配不到 <h2 class="">
String title = extract(block, "<h2>", "</h2>");
```

`indexOf("<h2>")` 要求 `<h2` 后面紧跟 `>`，但实际是 `<h2 `（后面是空格 + 属性），匹配不到 → 返回 null → 整条跳过 → 「未找到结果」。

### 改法

改用**兼容带属性标签的正则**：

```java
/** 提取指定标签内容，兼容带属性的标签（如 <h2 class="">）。 */
private static String extractTag(String s, String tag) {
    Matcher m = Pattern.compile("<" + tag + "[^>]*>(.*?)</" + tag + ">",
            Pattern.DOTALL | Pattern.CASE_INSENSITIVE).matcher(s);
    return m.find() ? m.group(1) : null;
}
```

顺带修掉一个连带 bug：Bing 的 `<cite>` 现在自带协议（`https://…`），旧代码又硬加一个 `https://`，导致 URL 变成 `https://https://…`。改成「没有协议前缀才补」：

```java
String url = cite != null ? cite.replaceAll("<[^>]+>", "").trim() : "";
if (url != null && !url.startsWith("http://") && !url.startsWith("https://")) {
    url = "https://" + url;
}
```

## 改造六：搜索 key 配置接入 —— search 节

### 背景

搜索本来有三条通道：智谱 GLM API（`GLM_SEARCH_API_KEY`）→ Brave API（`BRAVE_SEARCH_API_KEY`）→ Bing HTML 抓取（兜底）。但 key 只从 `System.getenv` 读，**配置不集中、不可发现**，用户不知道该在哪配。

### 改法

把搜索 key 纳入 `config.yaml` 配置体系，和 `DEEPSEEK_API_KEY` 一个套路：

**① `config.yaml` 加可选 `search` 节**：

```yaml
# 联网搜索 API key（可选，二选一；不配则回退到 Bing HTML 抓取）
search:
  glm_api_key: ${GLM_SEARCH_API_KEY:-}
  brave_api_key: ${BRAVE_SEARCH_API_KEY:-}
```

**② 新增 `SearchConfig` record** + 挂到 `AppConfig`：

```java
public record SearchConfig(String glmApiKey, String braveApiKey) { }

public record AppConfig(
        List<ProviderConfig> providers,
        String defaultProvider,
        SearchConfig search) {
    /** 兼容旧的两参构造（无搜索配置），search 置空。 */
    public AppConfig(List<ProviderConfig> providers, String defaultProvider) {
        this(providers, defaultProvider, null);
    }
}
```

**③ `ConfigLoader` 解析可选 `search` 节**（缺省/空 → null，不影响旧配置）：

```java
private static SearchConfig parseSearch(Object obj) {
    if (!(obj instanceof Map<?, ?> map)) return null;
    String glm = optional(map, "glm_api_key");
    String brave = optional(map, "brave_api_key");
    return (glm == null && brave == null) ? null : new SearchConfig(glm, brave);
}
```

**④ `WebSearchTool` 构造器注入 key**，配置优先、环境变量次之、HTML 兜底：

```java
private final String glmKey;
private final String braveKey;

public WebSearchTool() { this(null, null); }  // 兼容旧用法与测试
public WebSearchTool(String glmKey, String braveKey) { ... }

// execute 里：
String apiKey = firstNonBlank(glmKey, System.getenv("GLM_SEARCH_API_KEY"));
if (apiKey != null) return searchGlm(query, count, apiKey);
apiKey = firstNonBlank(braveKey, System.getenv("BRAVE_SEARCH_API_KEY"));
if (apiKey != null) return searchApi(query, count, apiKey);
return searchHtml(query, count);  // 兜底
```

`App` 启动时从 `AppConfig` 取 key 传入 `WebSearchTool`。

**优先级**：`config.yaml` 注入 > 环境变量 > HTML 抓取。不配任何 key 也永远能用（走 HTML）。

## 小结

这一章把 Rook 从「源码」变成「免装 Java 的绿色产物」，核心是三条链：**shade 打 fat jar → jlink/jpackage 生成 app-image → tar 归档**。打包不是「编译过了就完事」，一半工作量在**打包后才发现的问题**上：

| 坑 | 本质 | 解法 |
| :--- | :--- | :--- |
| 乱码 | 字节流 vs Unicode 直写 | 统一走 JLine `terminal.output()` |
| 资源丢失 | 源码路径在 jar 里不存在 | classpath 加载 + resources 打包 |
| 闪退 | config 缺失 | 打包时拷贝 config + .rook |
| 进程占用 | dll 被锁 | taskkill + 手动关窗口 |
| 搜索空结果 | `<h2 class="">` 匹配不上 | 正则兼容带属性标签 |
| key 散落 | 只读环境变量 | 纳入 `config.yaml` 的 search 节 |

这些改造的共同点：**开发环境和打包环境要跑同一套代码路径**——输出统一走 JLine、资源统一走 classpath、配置统一走 `config.yaml`。做到了，开发时怎么测，打包后就怎么跑。
