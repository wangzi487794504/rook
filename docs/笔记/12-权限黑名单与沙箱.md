# 12 — 权限①：黑名单 + 沙箱

## 这一章做什么

实现权限五层中的**前两层**：

- **黑名单**：用正则拦截已知的高危命令，不可绕过
- **路径沙箱**：限制文件操作只能在项目目录内，防止越权访问

**完成后你能做到：**

- AI 想执行 `rm -rf /`？直接拦截
- AI 想读 `/etc/passwd`？直接拒绝
- 这两层是最基础的安全网，不需要配置、不需要用户交互、任何模式下都生效

## 为什么需要

### 没有权限控制的风险

现在工具执行是完全开放的，AI 想干嘛干嘛：

```
用户：帮我清理一下临时文件
AI：好的，执行 rm -rf /tmp/*
（结果 AI 写错了，执行了 rm -rf /）
→ 整个系统没了
```

```
用户：帮我看看这个项目的配置
AI：好的，让我读一下 /etc/passwd
（AI 好奇，读了系统敏感文件）
→ 密码哈希泄露了
```

**太危险了。必须有安全控制。**

### 权限五层架构

完整的权限系统有五层，层层过滤：

```
工具调用请求
    │
    ▼
┌─────────────────────┐
│ 1. Blacklist 黑名单  │ ← 本章：已知高危命令，直接拦
└──────────┬──────────┘
           │
    ▼
┌─────────────────────┐
│ 2. PathSandbox 沙箱  │ ← 本章：文件操作限制在项目内
└──────────┬──────────┘
           │
    ▼
┌─────────────────────┐
│ 3. RuleEngine 规则   │ ← 下一章：YAML 自定义规则
└──────────┬──────────┘
           │
    ▼
┌─────────────────────┐
│ 4. PermissionMode    │ ← 下一章：四档模式（全允许/确认/白名单/全拒绝）
└──────────┬──────────┘
           │
    ▼
┌─────────────────────┐
│ 5. HumanInTheLoop    │ ← 下一章：用户确认弹窗
└──────────┬──────────┘
           │
    ▼
  允许执行
```

**前两层是硬安全网：**

- 不需要配置
- 不需要用户交互
- 任何模式下都生效
- 不可绕过

后面三层是可配置的、灵活的。

## 核心概念

### Blacklist（黑名单）

- 内置一组正则表达式
- 匹配到的命令直接拒绝
- 仅对 `exec_command` 工具生效
- 不可配置、不可绕过

### PathSandbox（路径沙箱）

- 限制文件操作只能在项目目录内
- 解析符号链接，防止逃逸
- 对所有文件相关工具生效（read/write/edit/glob/grep）

## 第一步：Blacklist — 黑名单

```java
// permission/Blacklist.java
package com.rook.permission;

import com.rook.tools.ToolCall;
import java.util.List;
import java.util.regex.Pattern;

public class Blacklist {

    // 内置高危命令正则列表
    private static final List<Pattern> DANGEROUS = List.of(
        // rm -rf /  或 rm -rf /xxx  删除根目录或系统目录
        Pattern.compile("rm\\s+.*-(r|rf|fr)\\s+/"),
        
        // mkfs  格式化磁盘
        Pattern.compile("mkfs"),
        
        // dd if=  磁盘操作
        Pattern.compile("dd\\s+if="),
        
        // > /dev/sd  重定向到磁盘设备
        Pattern.compile(">\\s*/dev/sd"),
        
        // chmod 777 /  给根目录全开权限
        Pattern.compile("chmod\\s+777\\s+/"),
        
        // fork bomb  进程炸弹
        Pattern.compile(Pattern.quote(":(){ :|:& };:"))
    );

    /**
     * 检查工具调用是否在黑名单中
     * @return allow 或 deny
     */
    public PermissionResult check(ToolCall call) {
        // 只检查 exec_command 工具
        if (!"exec_command".equals(call.name())) {
            return PermissionResult.allow();
        }

        // 取出命令字符串
        String cmd = String.valueOf(call.input().getOrDefault("command", ""));

        // 逐条正则匹配
        for (Pattern p : DANGEROUS) {
            if (p.matcher(cmd).find()) {
                return PermissionResult.deny(
                    "高危命令被黑名单拦截: " + cmd, 
                    "blacklist"
                );
            }
        }

        return PermissionResult.allow();
    }
}
```

### 逐段详解

#### 1. 为什么用正则不用字符串匹配？

命令的写法千变万化：

- `rm -rf /`
- `rm -fr /`
- `rm  -rf  /`
- `sudo rm -rf /`
- `rm -rf / --no-preserve-root`

用字符串 `contains("rm -rf /")` 匹配不了所有变体。

用正则可以灵活匹配：

```
Pattern.compile("rm\\s+.*-(r|rf|fr)\\s+/")
```

- `rm` — 以 rm 开头
- `\\s+` — 一个或多个空格
- `.*` — 中间任意内容
- `-(r|rf|fr)` — -r 或 -rf 或 -fr
- `\\s+/` — 后面跟空格和 /

#### 2. 每条正则详解

##### rm -rf /

```
Pattern.compile("rm\\s+.*-(r|rf|fr)\\s+/")
```

匹配删除根目录或系统目录的命令。

**会匹配：**

- `rm -rf /`
- `rm -fr /etc`
- `sudo rm -rf /usr`
- `rm -rf / --no-preserve-root`

**不会匹配（安全的）：**

- `rm -rf ./tmp` — 删当前目录下的
- `rm -rf /home/user/project/tmp` — 这个也会匹配到 /，但...

**注意：** 这条正则比较激进，只要 `rm -rf` 后面跟 `/` 开头的路径就拦。

- `rm -rf /home/user/project/tmp` 也会被拦
- 因为 `/home` 也是 `/` 开头
- 这是有意为之，删绝对路径的东西都比较危险，宁可错杀

##### mkfs

```
Pattern.compile("mkfs")
```

格式化磁盘，绝对危险。

**会匹配：**

- `mkfs.ext4 /dev/sda1`
- `mkfs -t ext4 /dev/sdb`

##### dd if=

```
Pattern.compile("dd\\s+if=")
```

dd 命令可以直接写磁盘，非常危险。

**会匹配：**

- `dd if=/dev/zero of=/dev/sda`
- `dd if=image.img of=/dev/sdb`

##### > /dev/sd

```
Pattern.compile(">\\s*/dev/sd")
```

重定向到磁盘设备，相当于直接写磁盘。

**会匹配：**

- `echo xxx > /dev/sda`
- `cat image > /dev/sdb`

##### chmod 777 /

```
Pattern.compile("chmod\\s+777\\s+/")
```

给根目录或系统目录全开权限。

**会匹配：**

- `chmod 777 /`
- `chmod 777 /etc`

##### fork bomb

```
Pattern.compile(Pattern.quote(":(){ :|:& };:"))
```

经典的 fork bomb，不断 fork 进程，把系统搞崩。

**`Pattern.quote()` 是什么？**

把字符串里的特殊字符转义，当成普通字符匹配。

因为 `:(){ :|:& };:` 里有很多正则特殊字符（括号、竖线、花括号），用 quote 转义一下。

#### 3. check 方法

```
public PermissionResult check(ToolCall call) {
    // 只检查 exec_command
    if (!"exec_command".equals(call.name())) {
        return PermissionResult.allow();
    }
    
    String cmd = String.valueOf(call.input().getOrDefault("command", ""));
    
    for (Pattern p : DANGEROUS) {
        if (p.matcher(cmd).find()) {
            return PermissionResult.deny("高危命令: " + cmd, "blacklist");
        }
    }
    
    return PermissionResult.allow();
}
```

**逻辑：**

1. 不是 exec_command 工具？直接放行（黑名单只管命令执行）
2. 取出命令字符串
3. 逐条正则匹配
4. 匹配到任何一条 → 拒绝
5. 都没匹配到 → 放行

#### 4. 为什么用 find () 不是 matches ()

|    方法     |                 行为                 |
| :---------: | :----------------------------------: |
|  `find()`   | 部分匹配，只要字符串里有一段匹配就行 |
| `matches()` | 整串匹配，整个字符串必须完全匹配正则 |

**我们要用 find ()。**

比如命令是 `sudo rm -rf /`：

- 正则是 `rm\s+.*-(r|rf|fr)\s+/`
- `find()` → 能匹配到中间的 `rm -rf /` → 正确拦截
- `matches()` → 整个字符串不匹配（前面有 sudo）→ 漏过了

**所以一定要用 find ()。**

## 第二步：PathSandbox — 路径沙箱

限制文件操作只能在项目目录内。

```java
// permission/PathSandbox.java
package com.rook.permission;

import com.rook.tools.ToolCall;
import java.nio.file.*;
import java.util.Set;

public class PathSandbox {

    // 需要检查路径的文件工具
    private static final Set<String> FILE_TOOLS = Set.of(
        "read_file", 
        "write_file", 
        "edit_file", 
        "glob", 
        "grep"
    );

    private final Path projectRoot;

    public PathSandbox(Path projectRoot) {
        this.projectRoot = projectRoot;
    }

    /**
     * 检查文件路径是否在项目目录内
     */
    public PermissionResult check(ToolCall call) {
        // 不是文件工具？放行
        if (!FILE_TOOLS.contains(call.name())) {
            return PermissionResult.allow();
        }

        // 取出路径参数（不同工具参数名可能不同）
        String pathStr = (String) call.input().get("filePath");
        if (pathStr == null) {
            pathStr = (String) call.input().get("path");
        }
        if (pathStr == null) {
            // 没有路径参数？放行（让工具自己处理参数错误）
            return PermissionResult.allow();
        }

        try {
            // 1. 解析路径：相对路径 → 绝对路径，去掉 . 和 ..
            Path target = projectRoot.resolve(pathStr).normalize();
            
            // 2. 如果文件存在，解析符号链接
            if (Files.exists(target)) {
                target = target.toRealPath();  // ★ 关键：解析 symlink
            }
            
            // 3. 获取项目根目录的真实路径
            Path realRoot = projectRoot.toRealPath();
            
            // 4. 前缀检查：目标路径必须以项目根目录开头
            if (!target.startsWith(realRoot)) {
                return PermissionResult.deny(
                    "路径超出项目范围: " + pathStr, 
                    "sandbox"
                );
            }
            
        } catch (Exception e) {
            // 路径检查出错，保守拒绝
            return PermissionResult.deny(
                "路径检查失败: " + e.getMessage(), 
                "sandbox"
            );
        }

        return PermissionResult.allow();
    }
}
```

### 逐段详解

#### 1. 为什么需要路径沙箱？

没有沙箱的话，AI 可以读写任何文件：

- 读 `/etc/passwd` — 系统敏感文件
- 读 `~/.ssh/id_rsa` — 私钥
- 写 `/etc/crontab` — 改定时任务
- 删 `/` — 删整个系统

**太危险了。必须限制 AI 只能操作项目目录内的文件。**

#### 2. 哪些工具需要检查？

```
private static final Set<String> FILE_TOOLS = Set.of(
    "read_file", 
    "write_file", 
    "edit_file", 
    "glob", 
    "grep"
);
```

所有操作文件的工具都要检查。

**exec_command 呢？**

exec_command 不在这里检查，因为命令里的路径太复杂（管道、重定向、多个文件），很难静态分析。

exec_command 由黑名单 + 后面的规则引擎 + 用户确认来控制。

#### 3. 路径解析三步

```
// 第 1 步：resolve + normalize
Path target = projectRoot.resolve(pathStr).normalize();
```

**resolve：** 把相对路径转成绝对路径。

- 项目根目录是 `/home/user/project`
- 用户传 `src/Main.java`
- resolve 后 → `/home/user/project/src/Main.java`

**normalize：** 去掉 `.` 和 `..`。

- 用户传 `src/../pom.xml`

- normalize 后 → `pom.xml`

- 但如果用户传 

  ```
  ../../etc/passwd
  ```

   呢？

  - resolve 后 → `/home/user/project/../../etc/passwd`
  - normalize 后 → `/home/etc/passwd`
  - 这就逃逸了！所以后面还要前缀检查

```
// 第 2 步：如果存在，解析符号链接
if (Files.exists(target)) {
    target = target.toRealPath();
}
```

**★ 这是最关键的一步，防止符号链接逃逸。**

什么是符号链接逃逸？

```java
项目目录: /home/user/project/

项目里有个符号链接:
  /home/user/project/link -> /etc/passwd

AI 想读 /etc/passwd，但直接读会被沙箱拦。
于是 AI 读项目里的符号链接:
  read_file("link")

如果不解析 symlink:
  target = /home/user/project/link
  startsWith(projectRoot) → true → 放行！
  但实际读的是 /etc/passwd → 逃逸成功！

如果解析 symlink:
  target = /home/user/project/link → toRealPath() → /etc/passwd
  startsWith(projectRoot) → false → 拦截！
```

**toRealPath () 会把符号链接解析成真实路径，这样前缀检查才有效。**

```java
// 第 3 步：前缀检查
Path realRoot = projectRoot.toRealPath();
if (!target.startsWith(realRoot)) {
    return PermissionResult.deny("路径超出项目范围", "sandbox");
}
```

**startsWith 检查：** 目标路径必须以项目根目录开头。

- `/home/user/project/src/Main.java` → 以 `/home/user/project` 开头 → 放行
- `/etc/passwd` → 不以 `/home/user/project` 开头 → 拦截

#### 4. 为什么 Files.exists () 和 toRealPath () 顺序不能反？

**错误顺序：**

```
target = target.toRealPath();  // 先 toRealPath
if (Files.exists(target)) {     // 再检查存在
    ...
}
```

**问题：** 如果文件不存在，toRealPath () 会抛异常！

**正确顺序：**

```
if (Files.exists(target)) {     // 先检查存在
    target = target.toRealPath();  // 存在才 toRealPath
}
```

**为什么？**

- toRealPath () 要求文件必须存在，否则抛 NoSuchFileException
- 但写文件的时候，目标文件可能还不存在（新建文件）
- 所以先检查存在，存在才解析 symlink
- 不存在的话，用 normalize 后的路径做前缀检查就行（还没创建，不可能有 symlink）

#### 5. 为什么检查出错要保守拒绝？

```
} catch (Exception e) {
    return PermissionResult.deny("路径检查失败", "sandbox");
}
```

路径检查出错了，说明可能有异常情况。这时候保守拒绝，宁可错杀不可放过。

**什么情况会出错？**

- 权限不够，读不了文件
- 符号链接成环
- 路径格式不对
- 其他 IO 异常

## PermissionResult — 权限结果

```java
// permission/PermissionResult.java
package com.rook.permission;

public record PermissionResult(
    boolean allowed,    // 是否允许
    String reason,      // 原因（拒绝时的说明）
    String layer        // 哪一层拦截的（blacklist/sandbox/...）
) {
    public static PermissionResult allow() {
        return new PermissionResult(true, null, null);
    }
    
    public static PermissionResult deny(String reason, String layer) {
        return new PermissionResult(false, reason, layer);
    }
    
    public boolean isDenied() {
        return !allowed;
    }
}
```

**统一的权限结果对象：**

- `allow()` — 允许
- `deny(reason, layer)` — 拒绝，带原因和拦截层

**layer 字段有什么用？**

记录是哪一层拦截的，方便调试和日志：

- `blacklist` — 黑名单拦的
- `sandbox` — 沙箱拦的
- `rule` — 规则引擎拦的
- `human` — 用户拒绝的

## 常见坑（详细版）

### 1. 符号链接逃逸

**现象：** AI 通过项目里的符号链接读到了项目外的文件。

**原因：** 没有调用 toRealPath () 解析符号链接。

**攻击方式：**

```
项目目录里有个符号链接:
  project/evil_link -> /etc/passwd

AI 调用 read_file("evil_link")
如果不解析 symlink:
  路径是 project/evil_link
  startsWith(projectRoot) → true → 放行
  但实际读的是 /etc/passwd → 逃逸！
```

**解决：** 文件存在时，调用 toRealPath () 解析符号链接，再做前缀检查。

### 2. 黑名单正则用 matches () 不用 find ()

**现象：** 有些高危命令没被拦到。

**原因：** 用了 matches () 而不是 find ()。

**对比：**

```
// 错误：matches() 要求整串匹配
p.matcher("sudo rm -rf /").matches()  // false，因为前面有 sudo

// 正确：find() 只要部分匹配就行
p.matcher("sudo rm -rf /").find()     // true，匹配到中间的 rm -rf /
```

**一定要用 find ()。**

### 3. Files.exists () 和 toRealPath () 顺序反了

**现象：** 新建文件时报错，或者路径检查异常。

**原因：** 先 toRealPath () 再检查 exists ()，文件不存在时 toRealPath () 抛异常。

**正确顺序：**

```
if (Files.exists(target)) {
    target = target.toRealPath();  // 存在才解析
}
```

### 4. Windows 路径问题

**现象：** Windows 上路径检查不正常。

**好消息：** Java 的 toRealPath () 和 startsWith () 在 Windows 上能正确处理：

- `D:\project\src\Main.java`
- 盘符前缀正确处理
- 反斜杠和正斜杠都能处理

**不需要特殊处理。**

但要注意：

- Windows 不区分大小写，`C:\Project` 和 `c:\project` 是同一个
- Java 的 startsWith () 是大小写敏感的
- 可能需要转成小写再比较

### 5. 黑名单正则不够全面

**现象：** 有些危险命令没被拦到。

**原因：** 黑名单不可能覆盖所有危险命令。

**比如：**

- `shutdown -h now` — 关机
- `reboot` — 重启
- `iptables -F` — 清防火墙
- `kill -9 -1` — 杀所有进程
- ...

**黑名单只是第一道防线，不是全部。**

后面还有规则引擎、权限模式、用户确认，多层防护。

### 6. 路径参数名不统一

**现象：** 有些工具的路径参数叫 `filePath`，有些叫 `path`，有些叫 `file`。

**解决：** 检查时多个参数名都试一下：

```
String pathStr = (String) call.input().get("filePath");
if (pathStr == null) pathStr = (String) call.input().get("path");
if (pathStr == null) pathStr = (String) call.input().get("file");
```

或者在工具定义里统一参数名。

### 7. glob/grep 的路径检查

**现象：** glob 和 grep 工具可能有 basePath 参数，也可能没有。

**glob 工具：**

- pattern 参数是匹配模式，不是路径
- basePath 才是起始目录
- 要检查 basePath

**grep 工具：**

- 可能有 basePath 参数
- 也可能直接搜当前目录

**要根据具体工具的参数来检查。**
