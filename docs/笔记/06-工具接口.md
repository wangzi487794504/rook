# 06 — Tool 接口 + ToolRegistry

## 这一章做什么

定义统一的 **Tool 接口** 和 **ToolRegistry 注册中心**。所有工具 —— 不管是内置的、MCP 远程的、还是 Skill 专属的 —— 都实现同一套契约。

**完成后你能做到：**

- 加新工具只需要写一个类，实现 Tool 接口
- Agent 循环不用关心工具具体怎么实现，只管调用
- 工具可以动态注册、动态卸载
- 统一的成功 / 失败返回格式

## 为什么需要

### 没有统一接口的痛点

想象一下，如果每个工具调用方式都不一样：

```java
if (toolName.equals("read_file")) {
    String content = fileTool.readFile(params.get("path"));
} else if (toolName.equals("exec")) {
    String output = execTool.runCommand(params.get("cmd"));
} else if (toolName.equals("mcp_everything_search")) {
    JsonNode result = mcpClient.callTool("search", params);
} else if ...
```

**问题：**

- 一堆 if-else，加新工具就要改这里
- 每个工具的参数格式、返回格式都不一样
- 上层代码要知道每个工具的细节
- 难以动态加载工具

### 有了统一接口之后

```java
Tool tool = registry.get(toolName);
ToolResult result = tool.execute(params);
```

**就这么简单。** 上层只认识 Tool 接口，不关心具体是哪个工具、怎么实现的。

**这就是面向接口编程的威力。**

## 核心概念

### Tool 接口

所有工具的统一契约，定义了 "一个工具应该长什么样"。

**四个核心方法：**

1. `name()` — 工具名字，唯一标识
2. `description()` — 工具描述，给 LLM 看的，告诉它这个工具能干什么
3. `inputSchema()` — 参数的 JSON Schema，告诉 LLM 该怎么填参数
4. `execute(params)` — 执行工具，返回结果

### ToolResult

工具执行结果的统一封装。

**两个字段：**

- `success` — 成功还是失败
- `content` — 成功时是结果内容，失败时是错误信息

**为什么需要统一的结果格式？**

- 上层不用关心每个工具怎么表示成功失败
- 出错了统一处理
- 返回给 LLM 的格式一致

### ToolCall

LLM 返回的 "工具调用请求"。

**三个字段：**

- `id` — 调用 ID，用来匹配请求和响应
- `name` — 要调用哪个工具
- `input` — 工具参数

**为什么需要这个类？**

LLM 返回的不是直接的结果，而是 "我想调用这个工具，参数是这些"。你需要把这个请求解析出来，然后实际去调用工具，再把结果返回给 LLM。

### ToolRegistry

工具注册中心，管理所有工具。

**功能：**

- 注册工具
- 按名字查找工具
- 卸载工具
- 列出所有工具
- 生成工具定义列表（给 LLM 看的）

**为什么需要注册中心？**

- 集中管理所有工具
- 动态增删工具
- 统一生成工具定义

## 第一步：Tool 接口

```java
// tools/Tool.java
package com.rook.tools;

import java.util.Map;

public interface Tool {
    String name();                          // 工具名，如 "read_file"
    String description();                   // 给 LLM 看的描述
    Map<String, Object> inputSchema();      // JSON Schema，参数格式
    ToolResult execute(Map<String, Object> params);  // 执行
}
```

### 四个方法详解

#### 1. name () — 工具名

```
String name();
```

**工具的唯一标识符。**

**命名规范：**

- 用小写字母 + 下划线
- 动词 + 名词的结构
- 不要带空格、特殊字符

**好的例子：**

- `read_file` — 读文件
- `write_file` — 写文件
- `exec_command` — 执行命令
- `grep_search` — 搜索

**不好的例子：**

- `ReadFile` — 大写，不统一
- `read file` — 有空格，LLM 容易搞错
- `file1` — 不知道干什么的

**为什么命名很重要？**

LLM 是根据名字来选择工具的。名字起得清晰，LLM 就更容易选对工具。

#### 2. description () — 工具描述

```
String description();
```

**给 LLM 看的，告诉它这个工具能干什么、什么时候用。**

**好的描述应该包含：**

- 工具是干什么的
- 什么时候用这个工具
- 什么时候不用

**例子：**

```
"读取指定路径的文件内容。用于查看文件内容、读取代码文件、读取配置文件等。"
```

**为什么 description 很重要？**

LLM 根据 description 来判断 "我现在该不该调用这个工具"。描述写得好，LLM 就不会乱调用工具。

#### 3. inputSchema () — 参数格式

```
Map<String, Object> inputSchema();
```

**告诉 LLM 该怎么填参数，用 JSON Schema 格式。**

**JSON Schema 是什么？**

一种描述 JSON 数据格式的标准。可以定义：

- 有哪些字段
- 每个字段是什么类型
- 哪些字段是必填的
- 字段的描述

**例子（read_file 的参数）：**

```java
{
  "type": "object",
  "properties": {
    "path": {
      "type": "string",
      "description": "要读取的文件路径"
    }
  },
  "required": ["path"]
}
```

**为什么需要 inputSchema？**

- LLM 知道该传什么参数
- 不会漏传必填字段
- 不会传错类型

**这是 Function Calling 的核心机制。**

#### 4. execute () — 执行

```
ToolResult execute(Map<String, Object> params);
```

**真正干活的方法。**

- 输入：参数 Map（LLM 填的）
- 输出：ToolResult（执行结果）

**实现类在这个方法里写具体逻辑。**

## 第二步：ToolResult

```java
// tools/ToolResult.java
package com.rook.tools;

public record ToolResult(boolean success, String content) {
    
    // 成功的快捷构造
    public static ToolResult ok(String content) {
        return new ToolResult(true, content);
    }
    
    // 失败的快捷构造
    public static ToolResult error(String msg) {
        return new ToolResult(false, msg);
    }
}
```

### 为什么用 record？

ToolResult 就是个纯数据载体，用 record 最合适：

- 不可变
- 自动生成构造器、getter、equals、hashCode
- 代码简洁

### 两个字段

|   字段    |  类型   |                含义                |
| :-------: | :-----: | :--------------------------------: |
| `success` | boolean |          执行成功还是失败          |
| `content` | String  | 成功时是结果内容，失败时是错误信息 |

### 两个静态工厂方法

**`ok(content)` — 成功**

```
return ToolResult.ok("文件内容是...");
```

**`error(msg)` — 失败**

```
return ToolResult.error("文件不存在: " + path);
```

**为什么要这两个方法？**

- 比 `new ToolResult(true, "...")` 更可读
- 调用方一眼就知道是成功还是失败
- 少写代码

### 使用示例

```java
// 成功
public ToolResult execute(Map<String, Object> params) {
    String path = (String) params.get("path");
    try {
        String content = Files.readString(Path.of(path));
        return ToolResult.ok(content);   // ✅ 成功
    } catch (IOException e) {
        return ToolResult.error("读取失败: " + e.getMessage());  // ❌ 失败
    }
}
```

## 第三步：ToolCall

```java
// tools/ToolCall.java
package com.rook.tools;

import java.util.Map;

/** LLM 返回的工具调用请求 */
public record ToolCall(
    String id,              // 调用 ID
    String name,            // 工具名
    Map<String, Object> input  // 参数
) {}
```

### 这是什么？

LLM 返回的 "我想调用工具" 的请求。

**不是工具执行的结果，是请求。**

### 三个字段

|  字段   |  含义   |                     用途                     |
| :-----: | :-----: | :------------------------------------------: |
|  `id`   | 调用 ID | 匹配请求和响应，LLM 用它知道是哪个调用的结果 |
| `name`  | 工具名  |                要调用哪个工具                |
| `input` |  参数   |    LLM 填的参数，传给工具的 execute 方法     |

### 为什么需要 id？

因为 LLM 可能一次请求调用多个工具：

```
LLM 返回：
  tool_call_1: 调用 read_file，参数 path=a.txt
  tool_call_2: 调用 read_file，参数 path=b.txt
```

你执行完两个工具，要把结果返回给 LLM：

```
你返回给 LLM：
  tool_result_1: id=tool_call_1, content=...
  tool_result_2: id=tool_call_2, content=...
```

**id 就是用来配对的**，LLM 知道哪个结果对应哪个调用。

### 完整的工具调用流程

```
1. 用户发消息
   ↓
2. LLM 返回：我要调用工具 A，参数是 xxx，id=123
   ↓ （解析成 ToolCall 对象）
3. 实际执行工具 A
   ↓
4. 把结果返回给 LLM：id=123，结果是 yyy
   ↓
5. LLM 根据工具结果生成最终回答
```

## 第四步：ToolRegistry

```java
// tools/ToolRegistry.java
package com.rook.tools;

import java.util.*;

public class ToolRegistry {

    // 存储所有工具：名字 → 工具对象
    private final Map<String, Tool> tools = new LinkedHashMap<>();

    // 注册工具
    public void register(Tool tool) {
        tools.put(tool.name(), tool);       // 同名覆盖
    }

    // 按名字查找
    public Optional<Tool> get(String name) {
        return Optional.ofNullable(tools.get(name));
    }

    // 卸载工具
    public void unregister(String name) {
        tools.remove(name);
    }

    // 列出所有工具名
    public Set<String> names() {
        return Collections.unmodifiableSet(tools.keySet());
    }

    // 工具数量
    public int size() { return tools.size(); }

    /** 生成工具定义列表，传给 LLM 的 API */
    public List<Map<String, Object>> toToolDefinitions() {
        List<Map<String, Object>> defs = new ArrayList<>();
        for (Tool t : tools.values()) {
            Map<String, Object> d = new LinkedHashMap<>();
            d.put("name", t.name());
            d.put("description", t.description());
            d.put("input_schema", t.inputSchema());
            defs.add(d);
        }
        return defs;
    }
}
```

### 这是什么？

工具注册中心，所有工具都在这里登记。

**就像一个 "工具字典"：**

- 往里放工具 → register
- 按名字取工具 → get
- 列出来有哪些工具 → names
- 生成给 LLM 看的工具列表 → toToolDefinitions

### 逐方法详解

#### 1. register () — 注册工具

```
public void register(Tool tool) {
    tools.put(tool.name(), tool);
}
```

把一个工具注册到 registry 里。

**同名覆盖：** 如果名字一样，新的会替换旧的。

**为什么用 LinkedHashMap？**

- 保持注册顺序
- 调试时看工具列表顺序稳定
- 比 HashMap 稍微慢一点，但工具数量少（十几个），完全不是问题

#### 2. get () — 查找工具

```java
public Optional<Tool> get(String name) {
    return Optional.ofNullable(tools.get(name));
}
```

按名字找工具。

**返回 Optional，不是直接返回 Tool：**

- 找不到时返回 Optional.empty ()
- 强迫调用方处理 "工具不存在" 的情况
- 不会 NullPointerException

**使用示例：**

```java
Optional<Tool> toolOpt = registry.get("read_file");
if (toolOpt.isPresent()) {
    Tool tool = toolOpt.get();
    // 调用工具
} else {
    // 工具不存在，报错
}
```

#### 3. unregister () — 卸载工具

```
public void unregister(String name) {
    tools.remove(name);
}
```

移除一个工具。

**什么时候用？**

- 动态加载 / 卸载插件
- 某些工具只在特定场景可用
- 测试时替换 mock 工具

#### 4. names () — 列出所有工具名

```java
public Set<String> names() {
    return Collections.unmodifiableSet(tools.keySet());
}
```

返回所有工具的名字。

**为什么是不可修改的 Set？**

防止外部代码直接修改内部的 keySet，破坏封装。

#### 5. size () — 工具数量

```
public int size() { return tools.size(); }
```

有多少个工具。

#### 6. toToolDefinitions () — 生成工具定义

```java
public List<Map<String, Object>> toToolDefinitions() {
    List<Map<String, Object>> defs = new ArrayList<>();
    for (Tool t : tools.values()) {
        Map<String, Object> d = new LinkedHashMap<>();
        d.put("name", t.name());
        d.put("description", t.description());
        d.put("input_schema", t.inputSchema());
        defs.add(d);
    }
    return defs;
}
```

**生成 LLM API 需要的工具定义列表。**

调用 LLM API 时，要把所有可用工具的定义传过去，LLM 才能知道 "我可以调用哪些工具"。

**输出格式（Anthropic API）：**

```json
[
  {
    "name": "read_file",
    "description": "读取文件内容",
    "input_schema": {
      "type": "object",
      "properties": {
        "path": {"type": "string"}
      },
      "required": ["path"]
    }
  },
  {
    "name": "write_file",
    ...
  }
]
```

**为什么每次都重新构造？**

- 工具可能动态变化（注册 / 卸载）
- 工具数量少（十几个），性能完全没问题
- 简单、不容易出错

**以后可以优化吗？**

可以加缓存，工具变化时才重新生成。但现在完全没必要，过早优化是万恶之源。

## 第五步：注册工具

实际使用时，在 App 启动时把所有工具注册进去。

```java
// App.java 中
ToolRegistry toolRegistry = new ToolRegistry();

// 内置工具
toolRegistry.register(new ReadFileTool());
toolRegistry.register(new WriteFileTool());
toolRegistry.register(new EditFileTool());
toolRegistry.register(new ExecCommandTool());
toolRegistry.register(new GlobTool());
toolRegistry.register(new GrepTool());

// MCP 外部工具（动态发现的）
mcpManager.discover(..., toolRegistry);

// Skill 系统工具
toolRegistry.register(new SkillTool(skillRegistry, cmdRegistry));
```

### 三种来源的工具

#### 1. 内置工具

- 写死在代码里的
- 程序启动就注册
- 比如读文件、写文件、执行命令

#### 2. MCP 远程工具

- 从 MCP Server 动态发现的
- 可能有很多个
- 比如 Everything 搜索、浏览器控制

#### 3. Skill 专属工具

- Skill 系统提供的
- 跟具体 Skill 相关
- 比如代码生成、文档生成

**统一接口的好处就在这里：不管工具从哪来，上层调用方式都一样。**

## 一个完整的工具实现示例

以 ReadFileTool 为例，看看实现一个工具长什么样：

```java
public class ReadFileTool implements Tool {

    @Override
    public String name() {
        return "read_file";
    }

    @Override
    public String description() {
        return "读取指定路径的文件内容。用于查看文件内容、读取代码文件、读取配置等。";
    }

    @Override
    public Map<String, Object> inputSchema() {
        Map<String, Object> schema = new LinkedHashMap<>();
        schema.put("type", "object");
        
        Map<String, Object> properties = new LinkedHashMap<>();
        Map<String, Object> pathProp = new LinkedHashMap<>();
        pathProp.put("type", "string");
        pathProp.put("description", "要读取的文件路径");
        properties.put("path", pathProp);
        schema.put("properties", properties);
        
        schema.put("required", List.of("path"));
        return schema;
    }

    @Override
    public ToolResult execute(Map<String, Object> params) {
        String path = (String) params.get("path");
        if (path == null || path.isBlank()) {
            return ToolResult.error("path 参数不能为空");
        }
        try {
            String content = Files.readString(Path.of(path));
            return ToolResult.ok(content);
        } catch (IOException e) {
            return ToolResult.error("读取文件失败: " + e.getMessage());
        }
    }
}
```

**四个方法，一个不多一个不少。** 这就是一个完整的工具。

## 常见坑（详细版）

### 1. 工具名不要带空格

**现象：** LLM 调用工具时找不到，或者名字搞错。

**原因：** 工具名带空格，比如 `"read file"`，LLM 容易把它当成两个词。

**正确做法：** 用下划线分隔，`read_file`。

**命名规范：**

- 全小写
- 单词之间用下划线
- 动词 + 名词结构
- 简短但清晰

### 2. inputSchema 必须是合法的 JSON Schema

**现象：** LLM 填的参数总是不对，缺字段、类型错。

**原因：** inputSchema 写得不对，LLM 理解错了参数格式。

**JSON Schema 的基本要素：**

- `type` — 类型（object、string、number、boolean、array）
- `properties` — 对象的字段列表
- `required` — 必填字段列表
- `description` — 每个字段的描述

**常见错误：**

- 忘了写 `required` → LLM 可能不传必填字段
- 字段描述不清楚 → LLM 不知道该填什么
- 类型写错（比如写了 `str` 不是 `string`）

### 3. toToolDefinitions () 每次都重新构造

**有人会问：每次调用都 new 一个 List，性能不浪费吗？**

**答案：完全不浪费。**

- 工具数量少（一般 6-20 个）
- 构造一次也就几毫秒
- 比起 LLM 调用的几秒，完全可以忽略

**什么时候需要缓存？**

- 工具数量上百个
- 每次 LLM 调用都要生成好几次
- 性能测试证明这是瓶颈

**现在完全没必要，简单比什么都重要。**

### 4. 工具执行不要抛异常

**现象：** 工具执行出错，抛了异常，整个 Agent 循环崩了。

**正确做法：** 捕获异常，返回 `ToolResult.error(...)`。

**为什么？**

- 工具失败是正常的（文件不存在、命令执行失败）
- 不应该因为一个工具失败就整个程序崩了
- 返回错误信息给 LLM，它可能自己想办法纠正

**反例：**

```
public ToolResult execute(Map<String, Object> params) throws IOException {
    // 直接抛异常，上层要处理
    String content = Files.readString(...);
    return ToolResult.ok(content);
}
```

**正例：**

```
public ToolResult execute(Map<String, Object> params) {
    try {
        String content = Files.readString(...);
        return ToolResult.ok(content);
    } catch (IOException e) {
        return ToolResult.error("失败: " + e.getMessage());  // ✅ 捕获，返回错误结果
    }
}
```

### 5. description 写得太简单

**现象：** LLM 不会用这个工具，或者乱用。

**原因：** description 太简单，LLM 不知道什么时候该用。

**反例：**

```
return "读文件";
```

**正例：**

```
return "读取指定路径的文本文件内容。" +
       "用于查看源代码、配置文件、文档等文本文件。" +
       "如果文件不存在或不是文本文件，会返回错误。" +
       "不要用这个工具读取二进制文件（图片、视频等）。";
```

**好的 description 应该告诉 LLM：**

- 这个工具是干什么的
- 什么时候用它
- 什么时候不要用它
- 有什么限制

### 6. 参数校验

**现象：** LLM 传的参数不对，工具执行出错。

**原因：** 没有校验参数，直接用。

**正确做法：** execute 方法开头先校验参数。

```
public ToolResult execute(Map<String, Object> params) {
    // 校验必填参数
    String path = (String) params.get("path");
    if (path == null || path.isBlank()) {
        return ToolResult.error("缺少必填参数: path");
    }
    
    // 校验参数格式
    if (path.contains("..")) {
        return ToolResult.error("path 不能包含 '..'，防止路径穿越");
    }
    
    // 正常执行
    ...
}
```

**为什么要校验？**

- LLM 有时候会传错参数
- 安全考虑（比如路径穿越）
- 给出清晰的错误信息，LLM 可能自己纠正

## 架构图

```
┌──────────────────────────────────────────────────────────┐
│                      Tool 接口                            │
│                                                          │
│  name() / description() / inputSchema() / execute()      │
└───────────┬──────────────────────────┬───────────────────┘
            │                          │
    ┌───────▼───────┐          ┌───────▼───────┐
    │  内置工具      │          │  MCP 工具      │
    │               │          │               │
    │ ReadFile      │          │ MCPTool 包装器  │
    │ WriteFile     │          │  （动态发现）    │
    │ ExecCommand   │          └───────────────┘
    │ Grep          │
    │ Glob          │          ┌───────────────┐
    │ ...           │          │  Skill 工具    │
    └───────────────┘          │               │
                               │ SkillTool     │
            │                  └───────────────┘
            │
            ▼
    ┌───────────────┐
    │ ToolRegistry  │  ← 注册中心，统一管理所有工具
    │               │
    │ register()    │
    │ get()         │
    │ toToolDefs()  │
    └───────┬───────┘
            │
            ▼
    ┌───────────────┐
    │  Agent Loop   │  ← 上层只认识 Tool 接口
    └───────────────┘
```

**核心思想：所有工具都实现同一个接口，上层只跟接口打交道。**
