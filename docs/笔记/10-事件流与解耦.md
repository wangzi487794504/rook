# 10 — 事件流：Agent 与 UI 解耦

## 这一章做什么

用 **BlockingQueue + AgentEvent** 把 AgentLoop 和终端 UI 解耦。Agent 在后台线程推事件，UI 在主线程消费事件 —— 互不阻塞，互不依赖。

**完成后你能做到：**

- Agent 和 UI 各跑各的，谁也不阻塞谁
- 换 UI（终端 → Web → GUI）不用改 Agent 代码
- 可以同时有多个消费者（比如同时显示到终端和写日志）
- Ctrl+C 取消 Agent，终端立刻回到提示符

## 为什么需要

### 紧耦合的痛点

之前的 AgentLoop 直接 `System.out.print(token)`，把输出写死在终端上。

**问题：**

- Agent 代码里混着 UI 逻辑（System.out）
- 想换个 Web 界面？Agent 代码要大改
- 想同时输出到终端和日志文件？麻烦
- 想做单元测试？还要捕获 System.out，麻烦

### 解耦之后

Agent 只管产生事件，不管谁来消费、怎么显示。

```
AgentLoop → 事件队列 → UI（终端/Web/GUI/日志/测试）
```

**好处：**

- Agent 和 UI 独立演化
- 可以有多个消费者
- 容易测试（直接检查队列里的事件）
- 符合单一职责原则

## 核心概念

### AgentEvent

事件对象，封装了 "发生了什么事"。

**7 种事件类型：**

- `TEXT` — LLM 输出了文本 token
- `TOOL_CALL` — LLM 决定调用工具
- `TOOL_RESULT` — 工具执行完了
- `TOKEN_USAGE` — token 用量统计
- `PROGRESS` — 进度更新（第几轮）
- `ERROR` — 出错了
- `DONE` — 全部完成

### BlockingQueue

阻塞队列，生产者 - 消费者模式的经典实现。

**Producer（生产者）：** AgentLoop 线程，往队列里 put 事件

**Consumer（消费者）：** UI 线程，从队列里 take/poll 事件

**为什么用 BlockingQueue？**

- 线程安全，多线程读写没问题
- 队列满了，生产者自动等待
- 队列空了，消费者自动等待
- 天然的流量控制

### StreamCollector

流式收集器，双路输出：

1. **实时推送** — 来一个 token 就往队列里发一个（实时显示）
2. **累积收集** — 同时攒起来，最后拿到完整结果（用于逻辑判断）

## 第一步：AgentEvent — 事件定义

```java
// core/agent/AgentEventType.java
public enum AgentEventType {
    TEXT,        // 文本 token
    TOOL_CALL,   // 工具调用开始
    TOOL_RESULT, // 工具执行结果
    TOKEN_USAGE, // token 用量
    PROGRESS,    // 进度更新
    ERROR,       // 错误
    DONE         // 全部完成
}
```

```java
// core/agent/AgentEvent.java
package com.rook.core.agent;

import com.rook.tools.ToolCall;
import com.rook.tools.ToolResult;

public record AgentEvent(
    AgentEventType type,           // 事件类型
    String text,                   // 文本内容（TEXT / ERROR 用）
    ToolCall toolCall,             // 工具调用（TOOL_CALL 用）
    ToolResult toolResult,         // 工具结果（TOOL_RESULT 用）
    int iteration,                 // 当前迭代（PROGRESS 用）
    int totalIterations            // 总迭代数（PROGRESS 用）
) {
    // 快捷构造方法
    public static AgentEvent text(String t) {
        return new AgentEvent(AgentEventType.TEXT, t, null, null, 0, 0);
    }
    
    public static AgentEvent toolCall(ToolCall tc) {
        return new AgentEvent(AgentEventType.TOOL_CALL, null, tc, null, 0, 0);
    }
    
    public static AgentEvent toolResult(ToolResult tr) {
        return new AgentEvent(AgentEventType.TOOL_RESULT, null, null, tr, 0, 0);
    }
    
    public static AgentEvent progress(int iter, int total) {
        return new AgentEvent(AgentEventType.PROGRESS, null, null, null, iter, total);
    }
    
    public static AgentEvent tokenUsage(String usage) {
        return new AgentEvent(AgentEventType.TOKEN_USAGE, usage, null, null, 0, 0);
    }
    
    public static AgentEvent error(String msg) {
        return new AgentEvent(AgentEventType.ERROR, msg, null, null, 0, 0);
    }
    
    public static AgentEvent done() {
        return new AgentEvent(AgentEventType.DONE, null, null, null, 0, 0);
    }
}
```

### 为什么用 record？

AgentEvent 是纯数据载体，用 record 最合适：

- 不可变
- 自动生成构造器、getter、equals、hashCode
- 代码简洁

### 为什么用静态工厂方法？

**对比：**

```java
// 不用工厂方法，每次都要写这么多
eventQueue.put(new AgentEvent(AgentEventType.TEXT, token, null, null, 0, 0));

// 用工厂方法，简洁清晰
eventQueue.put(AgentEvent.text(token));
```

**好处：**

- 代码更短
- 可读性更好（一眼就知道是什么事件）
- 不容易写错字段（比如把 text 放到 toolCall 里）
- 以后改构造器，调用方不用改

### 事件类型详解

|     类型      |      触发时机      |     携带数据     |      UI 怎么显示       |
| :-----------: | :----------------: | :--------------: | :--------------------: |
|    `TEXT`     | LLM 输出一个 token |       text       |  直接打印（打字效果）  |
|  `TOOL_CALL`  |  LLM 决定调用工具  |     toolCall     | 显示 "[调用工具: xxx]" |
| `TOOL_RESULT` |    工具执行完了    |    toolResult    | 显示 "[工具结果: ...]" |
|  `PROGRESS`   |     新一轮开始     | iteration, total |  显示 "[第 3/25 轮]"   |
| `TOKEN_USAGE` |     一轮结束后     | text（用量信息） |      显示用量统计      |
|    `ERROR`    |       出错了       | text（错误信息） |      显示红色错误      |
|    `DONE`     |      全部完成      |        无        |       回到提示符       |

## 第二步：AgentLoop — 生产者

AgentLoop 是生产者，往队列里推事件。

```javascript
// AgentLoop.run() 中的关键代码

// 1. 创建事件队列
BlockingQueue<AgentEvent> eventQueue = new LinkedBlockingQueue<>(1000);

// 2. 启动后台线程
new Thread(() -> {
    try {
        int iteration = 1;
        while (state == LoopState.RUNNING) {
            
            // 发进度事件
            eventQueue.put(AgentEvent.progress(iteration, maxIterations));
            
            // 准备收集器：来一个 token 就发一个 TEXT 事件
            StreamCollector collector = new StreamCollector(
                token -> {
                    try {
                        eventQueue.put(AgentEvent.text(token));
                    } catch (InterruptedException e) {
                        Thread.currentThread().interrupt();
                    }
                });
            
            // 调 LLM
            provider.stream(history, tools, collector);
            
            // 拿到工具调用列表
            List<ToolCall> toolCalls = collector.getToolCalls();
            
            if (toolCalls.isEmpty()) {
                // 没有工具调用 → 完成
                break;
            }
            
            // 发工具调用事件
            for (ToolCall tc : toolCalls) {
                eventQueue.put(AgentEvent.toolCall(tc));
            }
            
            // 执行工具
            List<ToolResult> results = executor.execute(toolCalls);
            
            // 发工具结果事件
            for (ToolResult tr : results) {
                eventQueue.put(AgentEvent.toolResult(tr));
            }
            
            // ... 回灌历史，继续下一轮
            
            iteration++;
        }
    } finally {
        // 最后一定发 DONE
        eventQueue.put(AgentEvent.done());
    }
}, "agent-loop").start();

return eventQueue;  // 返回队列给调用方
```

### 逐段详解

#### 1. 创建队列

```
BlockingQueue<AgentEvent> eventQueue = new LinkedBlockingQueue<>(1000);
```

**LinkedBlockingQueue 是什么？**

- 基于链表的阻塞队列
- 线程安全
- 有容量限制（这里是 1000）

**为什么容量设 1000？**

- 正常对话不会有这么多事件
- 作为安全上限，防止内存爆掉
- 1000 个事件，每个几十字节，总共也就几十 KB，完全没问题

#### 2. 后台线程

```
new Thread(() -> {
    // ... 循环逻辑
}, "agent-loop").start();
```

Agent 在单独的线程里跑，不阻塞 UI 线程。

**线程名 "agent-loop"：**

- 给线程起个名字，调试的时候方便看
- jstack、日志里能识别出来

#### 3. 流式 token → TEXT 事件

```java
StreamCollector collector = new StreamCollector(
    token -> {
        try {
            eventQueue.put(AgentEvent.text(token));
        } catch (InterruptedException e) {
            Thread.currentThread().interrupt();
        }
    });
```

**每来一个 token，就往队列里发一个 TEXT 事件。**

**为什么用 lambda？**

StreamCollector 需要一个回调，token 来了就调用这个回调。

我们的回调就是：把 token 包装成事件，放到队列里。

**InterruptedException 处理：**

put 方法可能被中断，中断后恢复中断标记，让上层知道。

#### 4. 工具调用 → TOOL_CALL 事件

```java
for (ToolCall tc : toolCalls) {
    eventQueue.put(AgentEvent.toolCall(tc));
}
```

LLM 决定调用工具了，发事件通知 UI。

#### 5. 工具结果 → TOOL_RESULT 事件

```java
for (ToolResult tr : results) {
    eventQueue.put(AgentEvent.toolResult(tr));
}
```

工具执行完了，发事件通知 UI。

#### 6. 最后一定发 DONE

```java
finally {
    eventQueue.put(AgentEvent.done());
}
```

**不管正常还是异常，最后一定发一个 DONE 事件。**

**为什么？**

消费者需要知道什么时候结束。如果没有 DONE，消费者会一直等下去。

**这是一个约定：事件流的最后一个事件一定是 DONE。**

## 第三步：Repl — 消费者

Repl 是消费者，从队列里取事件，显示到终端。

```java
// Repl.java 中的消费逻辑

public void consumeEvents(BlockingQueue<AgentEvent> eventQueue) {
    StringBuilder fullReply = new StringBuilder();
    
    while (true) {
        // 从队列里取事件，最多等 100ms
        AgentEvent event = eventQueue.poll(100, TimeUnit.MILLISECONDS);
        
        // 超时了，没取到事件
        if (event == null) {
            // 检查用户有没有按 Ctrl+C
            if (userWantsToCancel) {
                agentLoop.cancel();
                continue;
            }
            continue;
        }

        // 根据事件类型做不同处理
        switch (event.type()) {
            
            case TEXT -> {
                // 文本 token → 直接打印
                System.out.print(event.text());
                System.out.flush();
                fullReply.append(event.text());
            }
            
            case TOOL_CALL -> {
                // 工具调用 → 显示提示
                System.out.println();
                System.out.println("[调用工具: " + event.toolCall().name() + "]");
            }
            
            case TOOL_RESULT -> {
                // 工具结果 → 可以显示摘要
                // （完整结果不一定要全显示，太长了）
                System.out.println("[工具执行完成]");
            }
            
            case PROGRESS -> {
                // 进度 → 显示第几轮
                System.out.println();
                System.out.println("[第 " + event.iteration() + "/" + event.totalIterations() + " 轮]");
            }
            
            case ERROR -> {
                // 错误 → 显示错误信息
                System.err.println("[错误: " + event.text() + "]");
                return;  // 结束消费
            }
            
            case DONE -> {
                // 完成 → 退出循环
                System.out.println();
                return;
            }
            
            default -> {
                // 其他事件忽略，或者做默认处理
            }
        }
    }
}
```

### 逐段详解

#### 1. poll () 还是 take ()？

```
AgentEvent event = eventQueue.poll(100, TimeUnit.MILLISECONDS);
```

**两种取事件的方式：**

|      方法       |           行为            |        队列空时        |
| :-------------: | :-----------------------: | :--------------------: |
|    `take()`     |   阻塞等待，直到有事件    |         一直等         |
| `poll(timeout)` | 等一段时间，超时返回 null | 等 timeout 后返回 null |

**为什么用 poll (100ms) 不用 take ()？**

因为要检测 Ctrl+C 取消。

如果用 take ()，线程会一直阻塞在那里等事件，这时候用户按 Ctrl+C，线程没醒过来，就响应不了。

用 poll (100ms)，每 100ms 醒一次，检查一下用户是不是取消了，如果是就取消 Agent，然后继续等。

**100ms 的意义：**

- 足够短，用户感觉不到延迟
- 足够长，不会空转浪费 CPU

#### 2. 空事件处理

```
if (event == null) {
    if (userWantsToCancel) {
        agentLoop.cancel();
    }
    continue;
}
```

poll 超时了，没取到事件。

这时候检查一下：

- 用户是不是想取消？（按了 Ctrl+C）
- 如果是，就调用 agentLoop.cancel ()
- 然后继续循环，等 DONE 事件

#### 3. TEXT 事件

```java
case TEXT -> {
    System.out.print(event.text());
    System.out.flush();
    fullReply.append(event.text());
}
```

**做三件事：**

1. 打印 token（打字效果）
2. flush 缓冲区，确保立刻显示
3. 同时攒起来，后面可能要用

#### 4. TOOL_CALL 事件

```
case TOOL_CALL -> {
    System.out.println();
    System.out.println("[调用工具: " + event.toolCall().name() + "]");
}
```

显示 "调用工具了" 的提示，让用户知道 AI 在干嘛。

#### 5. ERROR 事件

```
case ERROR -> {
    System.err.println("[错误: " + event.text() + "]");
    return;  // 结束消费
}
```

出错了，显示错误，然后退出。

#### 6. DONE 事件

```
case DONE -> {
    System.out.println();
    return;
}
```

全部完成了，退出消费循环，回到提示符。

## 生产者 - 消费者模式详解

### 什么是生产者 - 消费者模式？

经典的多线程设计模式：

- **生产者**：产生数据，放到队列里
- **消费者**：从队列里取数据，处理
- **队列**：缓冲区，解耦生产者和消费者

**为什么好？**

- 生产者和消费者速度不一样也没关系
- 队列起缓冲作用
- 可以有多个生产者、多个消费者
- 两边独立演化，互不影响

### 在我们的场景里

- **生产者**：AgentLoop 线程，产生事件
- **消费者**：Repl 主线程，消费事件显示到终端
- **队列**：BlockingQueue<AgentEvent>

**速度差异怎么处理？**

- Agent 产生 token 的速度：每秒几十个
- UI 消费的速度：打印很快
- 队列里一般不会积压太多

**如果 UI 很慢怎么办？**

- 队列会积压
- 队列满了，put 就阻塞
- Agent 就慢下来
- 自然的流量控制

## 常见坑（详细版）

### 1. 事件队列满了

**现象：** Agent 线程卡住了，不往下跑。

**原因：** 队列满了，put 方法阻塞等待。

**什么时候会满？**

- 消费者太慢，消费不过来
- 生产者太快，产生太多事件
- 消费者挂了，没人消费

**正常情况会满吗？**

- 不会，正常对话 token 产生速度远小于消费速度
- 1000 的容量绰绰有余

**如果真的满了怎么办？**

- 检查消费者是不是卡住了
- 或者用 offer + 丢弃策略，保证不阻塞（但可能丢事件）

### 2. 消费线程退出过早

**现象：** 还没结束，UI 就退回去了。

**原因：** 没有等 DONE 事件，遇到某个事件就退了。

**正确做法：**

- 只有遇到 DONE 或 ERROR 才退出
- 其他事件都继续等

**为什么 DONE 这么重要？**

DONE 是 "结束" 的唯一信号。没有 DONE，你不知道是真的结束了，还是暂时没事件。

### 3. poll 超时设太长

**现象：** 按 Ctrl+C 之后，要等好久才响应。

**原因：** poll 超时设太长，比如 5 秒。线程阻塞在 poll 里，要等超时了才醒过来检查取消标志。

**我们设 100ms 的原因：**

- 足够短，用户按 Ctrl+C 后最多等 100ms 就响应
- 足够长，不会频繁空转浪费 CPU

### 4. 用 take () 不用 poll ()

**现象：** Ctrl+C 完全没反应。

**原因：** take () 会无限阻塞，线程醒不过来，就检查不了取消标志。

**解决：** 用 poll (timeout)，定期醒过来检查。

### 5. 事件顺序错乱

**现象：** 显示的顺序不对，比如工具结果在工具调用前面。

**原因：** 多线程并发问题，或者 put 的顺序不对。

**保证顺序的方法：**

- 单线程生产（AgentLoop 只有一个线程）
- 按逻辑顺序 put
- 队列是 FIFO（先进先出），put 的顺序就是 take 的顺序

### 6. 中断处理不当

**现象：** 中断后线程状态不对，或者吞掉了中断。

**正确处理 InterruptedException：**

```
try {
    eventQueue.put(event);
} catch (InterruptedException e) {
    Thread.currentThread().interrupt();  // 恢复中断标记
    // 然后根据情况决定是退出还是继续
}
```

**不要吞掉中断！** 捕获了之后要么重新抛出，要么恢复中断标记。

### 7. 忘记发 DONE

**现象：** UI 永远等在那里，不退出。

**原因：** 某个异常路径没发 DONE。

**解决：** 用 try-finally，确保不管正常还是异常，最后一定发 DONE。



```
try {
    // ... 主循环
} finally {
    eventQueue.put(AgentEvent.done());  // 一定发
}
```

```
              │     BlockingQueue<AgentEvent> │  ← 事件队列（缓冲区）
              │     [TEXT][TEXT][TOOL_CALL]...│
              └───────────────┬───────────────┘
                              │
                              ▼
┌─────────────────────────────────────────────────────────────────┐
│                        Repl（消费者）                             │
│                                                                 │
│  poll(100ms) → 取事件 → switch 处理 → 显示到终端                  │
│                                                                 │
│  TEXT → 打印                                                    │
│  TOOL_CALL → 显示提示                                           │
│  DONE → 退出                                                    │
└─────────────────────────────────────────────────────────────────┘
```

**核心思想：Agent 和 UI 通过队列通信，互不依赖。**
