# 13 — 权限②：规则引擎 + 模式兜底 + 人在回路

## 这一章做什么

实现权限五层的**后三层**：

- **规则引擎**：用户用 YAML 精确控制哪些工具允许、哪些拒绝
- **权限模式**：四档全局模式，一键切换整体权限
- **人在回路**：拿不准的操作，弹窗问用户

**完成后你能做到：**

- 用户写一条规则："只允许 git 命令" → 其他命令都被拦
- 用户输入 `:mode plan` → 立刻进入只读模式，所有写入都被拒
- AI 想改文件 → 弹窗问用户 "允许吗？"，用户按 1/2/3 决定

## 为什么需要

### 前两层的局限

黑名单和沙箱是**兜底的硬安全网**，但太粗暴：

- **黑名单**：只能拦已知的高危命令，不能精细控制
  - 想 "只允许 git 命令"？黑名单做不到
  - 想 "禁止 npm install"？黑名单也做不到
- **沙箱**：只能限制路径范围，不能控制具体操作
  - 想 "只读模式，不能改文件"？沙箱做不到
  - 想 "允许读但不允许写"？沙箱也做不到

### 后三层的价值

|   层级   |                  作用                   | 灵活性 |
| :------: | :-------------------------------------: | :----: |
| 规则引擎 | 精确控制：哪些工具、哪些参数允许 / 拒绝 |   高   |
| 权限模式 |     全局切换：一键切换整体权限策略      |   中   |
| 人在回路 |        最后确认：拿不准的问用户         |  最高  |

**三层配合，既安全又灵活。**

## 核心概念

### RuleEngine（规则引擎）

- 用户用 YAML 写规则
- 三层配置：local > project > user（优先级从高到低）
- 按工具名 + 参数 glob 匹配
- 命中规则 → allow 或 deny
- 没命中 → 穿透到下一层

### PermissionMode（权限模式）

- 四档全局模式
- 按工具类型（READ/WRITE/EXEC）分别控制
- 每类工具可以是 ALLOW / ASK / DENY

### HumanInTheLoop（人在回路）

- 终端弹窗确认
- 读单字符：1 = 允许本次，2 = 永久允许，3 = 拒绝
- 永久允许会自动写入规则文件

------

## 第一步：规则 YAML 格式

用户用 YAML 写自定义规则。

```yaml
# ~/.rook/rules.yaml （用户级规则）

rules:
  # 允许所有 git 命令
  - tool: exec_command
    pattern: "git *"
    action: allow
    
  # 禁止删除 .class 文件
  - tool: write_file
    pattern: "*.class"
    action: deny
    
  # 禁止执行 npm install
  - tool: exec_command
    pattern: "npm install*"
    action: deny
    
  # 允许读 src 目录下的所有文件
  - tool: read_file
    pattern: "src/**"
    action: allow
```

### 规则字段详解

|   字段    |             含义              |             示例             |
| :-------: | :---------------------------: | :--------------------------: |
|  `tool`   |            工具名             | `exec_command`、`write_file` |
| `pattern` | glob 匹配模式，匹配工具的参数 |      `git *`、`*.class`      |
| `action`  |    动作：`allow` 或 `deny`    |           `allow`            |

### 三层配置

规则分三层，优先级从高到低：

|  层级   |            路径            |             作用             | 优先级 |
| :-----: | :------------------------: | :--------------------------: | :----: |
|  local  | `./.rook/rules.local.yaml` | 当前项目本地规则，不提交 git |  最高  |
| project |    `./.rook/rules.yaml`    |  项目共享规则，可以提交 git  |   中   |
|  user   |    `~/.rook/rules.yaml`    |  用户全局规则，所有项目生效  |  最低  |

**为什么分三层？**

- **local**：个人临时规则，比如 "我这台机器上允许 xxx"，不分享给别人
- **project**：项目团队共享的规则，比如 "这个项目禁止直接改 main 分支"
- **user**：用户个人偏好，比如 "我所有项目都不允许 rm -rf"

**合并规则：** 三层都加载，按优先级排序，高优先级的规则先匹配。

## 第二步：RuleEngine — 规则引擎

```java
// permission/RuleEngine.java
package com.rook.permission;

import com.rook.tools.ToolCall;
import java.nio.file.*;
import java.util.*;
import java.util.regex.Pattern;

public class RuleEngine {

    private final List<RuleConfig> mergedRules;

    public RuleEngine(Path projectRoot) {
        this.mergedRules = loadRules(projectRoot);
    }

    /**
     * 加载三层规则，按优先级合并
     */
    private List<RuleConfig> loadRules(Path projectRoot) {
        List<RuleConfig> rules = new ArrayList<>();
        
        // 优先级从高到低加载，高优先级放前面
        // 1. local（最高优先级）
        rules.addAll(loadYaml(projectRoot.resolve(".rook/rules.local.yaml")));
        // 2. project
        rules.addAll(loadYaml(projectRoot.resolve(".rook/rules.yaml")));
        // 3. user（最低优先级）
        rules.addAll(loadYaml(Path.of(System.getProperty("user.home"), ".rook/rules.yaml")));
        
        return rules;
    }

    /**
     * 检查工具调用是否命中规则
     */
    public PermissionResult check(ToolCall call) {
        for (RuleConfig rule : mergedRules) {
            // 工具名不匹配，跳过
            if (!call.name().equals(rule.toolName())) {
                continue;
            }
            
            // 提取要匹配的参数
            String param = extractParam(call);
            
            // pattern 为空 → 匹配所有
            // pattern 不为空 → glob 匹配
            if (rule.pattern() == null || globMatch(rule.pattern(), param)) {
                if (rule.allow()) {
                    return PermissionResult.allow();
                } else {
                    return PermissionResult.deny(
                        "规则拒绝: " + rule.toolName() + " " + param,
                        "rule"
                    );
                }
            }
        }
        
        // 没命中任何规则 → 穿透，让下一层处理
        return PermissionResult.allow();
    }

    /**
     * 提取工具的主要参数用于匹配
     */
    private String extractParam(ToolCall call) {
        return switch (call.name()) {
            case "exec_command" -> String.valueOf(call.input().getOrDefault("command", ""));
            case "read_file", "write_file", "edit_file" -> 
                String.valueOf(call.input().getOrDefault("filePath", ""));
            case "glob", "grep" -> 
                String.valueOf(call.input().getOrDefault("pattern", ""));
            default -> "";
        };
    }

    /**
     * glob 模式匹配
     */
    private boolean globMatch(String pattern, String text) {
        // 把 glob 转成正则
        String regex = globToRegex(pattern);
        return Pattern.compile(regex).matcher(text).matches();
    }

    private String globToRegex(String glob) {
        StringBuilder regex = new StringBuilder("^");
        for (int i = 0; i < glob.length(); i++) {
            char c = glob.charAt(i);
            switch (c) {
                case '*' -> {
                    if (i + 1 < glob.length() && glob.charAt(i + 1) == '*') {
                        regex.append(".*");  // ** 匹配任意字符（包括 /）
                        i++;
                    } else {
                        regex.append("[^/]*");  // * 匹配除 / 外的任意字符
                    }
                }
                case '?' -> regex.append("[^/]");  // ? 匹配单个字符
                case '.' -> regex.append("\\.");   // . 转义
                default -> regex.append(c);
            }
        }
        regex.append("$");
        return regex.toString();
    }

    // 规则配置 record
    private record RuleConfig(
        String toolName,
        String pattern,
        boolean allow
    ) {}
}
```

### 逐段详解

#### 1. 加载三层规则

```java

    List<RuleConfig> rules = new ArrayList<>();
    
    // 高优先级放前面
    rules.addAll(loadYaml(projectRoot.resolve(".rook/rules.local.yaml")));
    rules.addAll(loadYaml(projectRoot.resolve(".rook/rules.yaml")));
    rules.addAll(loadYaml(Path.of(System.getProperty("user.home"), ".rook/rules.yaml")));
    
    return rules;

```

**按优先级从高到低加载，高优先级的规则放列表前面。**

后面 check 的时候，从前往后遍历，先匹配到的先生效。

#### 2. check 方法

```java
public PermissionResult check(ToolCall call) {
    for (RuleConfig rule : mergedRules) {
        // 工具名不匹配，跳过
        if (!call.name().equals(rule.toolName())) {
            continue;
        }
        
        String param = extractParam(call);
        
        if (rule.pattern() == null || globMatch(rule.pattern(), param)) {
            if (rule.allow()) {
                return PermissionResult.allow();
            } else {
                return PermissionResult.deny("规则拒绝: ...", "rule");
            }
        }
    }
    
    // 没命中 → 穿透
    return PermissionResult.allow();
}
```

**逻辑：**

1. 遍历所有规则（按优先级排序）
2. 工具名不匹配 → 跳过
3. 工具名匹配 → 检查参数是否匹配 pattern
4. 匹配到 → 返回 allow 或 deny
5. 都没匹配到 → 返回 allow（穿透到下一层）

**"穿透" 是什么意思？**

规则引擎没命中，不代表允许，而是 "我不管，让下一层来决定"。

所以返回 allow，但后面还有模式层和人在回路层继续检查。

#### 3. extractParam — 提取参数

```java
private String extractParam(ToolCall call) {
    return switch (call.name()) {
        case "exec_command" -> String.valueOf(call.input().getOrDefault("command", ""));
        case "read_file", "write_file", "edit_file" -> 
            String.valueOf(call.input().getOrDefault("filePath", ""));
        case "glob", "grep" -> 
            String.valueOf(call.input().getOrDefault("pattern", ""));
        default -> "";
    };
}
```

不同工具的主要参数不一样：

- exec_command → command
- 文件工具 → filePath
- 搜索工具 → pattern

提取出来，用于 glob 匹配。

#### 4. glob 匹配

```
private boolean globMatch(String pattern, String text) {
    String regex = globToRegex(pattern);
    return Pattern.compile(regex).matcher(text).matches();
}
```

把 glob 模式转成正则，然后匹配。

**glob 语法：**

|   glob   |           含义           |     正则      |
| :------: | :----------------------: | :-----------: |
|   `*`    | 匹配除 `/` 外的任意字符  |    `[^/]*`    |
|   `**`   | 匹配任意字符（包括 `/`） |     `.*`      |
|   `?`    |       匹配单个字符       |    `[^/]`     |
| `*.java` |     匹配 .java 文件      | `[^/]*\.java` |
| `src/**` |     匹配 src 下所有      |   `src/.*`    |

**为什么 `\*` 不匹配 `/`？**

这是 glob 的标准行为，`*` 只匹配当前目录，不跨目录。

跨目录要用 `**`。

## 第三步：PermissionMode — 权限模式

四档全局模式，一键切换整体权限。

```java
// permission/PermissionMode.java
package com.rook.permission;

import java.util.Map;
import java.util.Set;

public enum PermissionMode {

    // 默认模式：读放行，写和执行要确认
    DEFAULT(
        Map.of(
            ToolType.READ, PermissionVerdict.ALLOW,
            ToolType.WRITE, PermissionVerdict.ASK,
            ToolType.EXEC, PermissionVerdict.ASK
        )
    ),
    
    // 接受编辑：读和写都放行，执行要确认
    ACCEPT_EDITS(
        Map.of(
            ToolType.READ, PermissionVerdict.ALLOW,
            ToolType.WRITE, PermissionVerdict.ALLOW,
            ToolType.EXEC, PermissionVerdict.ASK
        )
    ),
    
    // 计划模式：读放行，写和执行都拒绝
    PLAN(
        Map.of(
            ToolType.READ, PermissionVerdict.ALLOW,
            ToolType.WRITE, PermissionVerdict.DENY,
            ToolType.EXEC, PermissionVerdict.DENY
        )
    ),
    
    // 绕过模式：全部放行（危险！）
    BYPASS(
        Map.of(
            ToolType.READ, PermissionVerdict.ALLOW,
            ToolType.WRITE, PermissionVerdict.ALLOW,
            ToolType.EXEC, PermissionVerdict.ALLOW
        )
    );

    private final Map<ToolType, PermissionVerdict> map;

    PermissionMode(Map<ToolType, PermissionVerdict> map) {
        this.map = map;
    }

    // 工具类型分类
    private static final Set<String> READ_TOOLS = Set.of("read_file", "glob", "grep");
    private static final Set<String> WRITE_TOOLS = Set.of("write_file", "edit_file");
    private static final Set<String> EXEC_TOOLS = Set.of("exec_command");

    /**
     * 根据工具名，返回该模式下的裁决
     */
    public PermissionVerdict verdictFor(String toolName) {
        if (READ_TOOLS.contains(toolName)) {
            return map.get(ToolType.READ);
        }
        if (WRITE_TOOLS.contains(toolName)) {
            return map.get(ToolType.WRITE);
        }
        if (EXEC_TOOLS.contains(toolName)) {
            return map.get(ToolType.EXEC);
        }
        // 未知工具，默认要确认
        return PermissionVerdict.ASK;
    }

    // 工具类型
    private enum ToolType { READ, WRITE, EXEC }
}

// 裁决结果
enum PermissionVerdict {
    ALLOW,   // 允许
    ASK,     // 问用户
    DENY     // 拒绝
}
```

### 四档模式详解

#### 1. DEFAULT（默认模式）

|   工具类型   | 裁决  |       说明       |
| :----------: | :---: | :--------------: |
|  READ（读）  | ALLOW |  读文件直接放行  |
| WRITE（写）  |  ASK  |  改文件要问用户  |
| EXEC（执行） |  ASK  | 执行命令要问用户 |

**最安全的默认模式：** 只读的随便看，要改东西或跑命令都得用户同意。

#### 2. ACCEPT_EDITS（接受编辑模式）

| 工具类型 | 裁决  |     说明     |
| :------: | :---: | :----------: |
|   READ   | ALLOW |    读放行    |
|  WRITE   | ALLOW |   写也放行   |
|   EXEC   |  ASK  | 执行命令要问 |

**适合：** 让 AI 自由改代码，但执行命令还是要确认。

比如重构代码、批量修改，不用每次都确认。

#### 3. PLAN（计划模式）

| 工具类型 | 裁决  |     说明     |
| :------: | :---: | :----------: |
|   READ   | ALLOW |    读放行    |
|  WRITE   | DENY  |  写直接拒绝  |
|   EXEC   | DENY  | 执行直接拒绝 |

**适合：** 只让 AI 分析，不让它动手。

比如 "帮我看看这个项目的架构"，AI 只能读，不能改。

#### 4. BYPASS（绕过模式）

| 工具类型 | 裁决  |   说明   |
| :------: | :---: | :------: |
|   READ   | ALLOW | 全部放行 |
|  WRITE   | ALLOW | 全部放行 |
|   EXEC   | ALLOW | 全部放行 |

**最危险的模式：** AI 想干嘛干嘛。

**注意：** 即使 BYPASS，黑名单和沙箱仍然生效！这两层是硬安全网，不可绕过。

### verdictFor 方法

```
public PermissionVerdict verdictFor(String toolName) {
    if (READ_TOOLS.contains(toolName)) return map.get(ToolType.READ);
    if (WRITE_TOOLS.contains(toolName)) return map.get(ToolType.WRITE);
    if (EXEC_TOOLS.contains(toolName)) return map.get(ToolType.EXEC);
    return PermissionVerdict.ASK;  // 未知工具默认要确认
}
```

**根据工具名判断类型，然后返回该模式下的裁决。**

未知工具默认 ASK，保守处理。

## 第四步：HumanInTheLoop — 人在回路

拿不准的操作，弹窗问用户。

```java
// permission/HumanInTheLoop.java
package com.rook.permission;

import com.rook.tools.ToolCall;
import org.jline.reader.LineReader;

public class HumanInTheLoop {

    /**
     * 询问用户是否允许执行
     * @return 允许 / 永久允许 / 拒绝
     */
    public HumanDecision ask(ToolCall call, String reason, LineReader reader) {
        // 显示提示
        System.err.println();
        System.err.println("⚠️  需要确认: " + reason);
        System.err.println("   工具: " + call.name());
        System.err.println("   参数: " + call.input());
        System.err.print("   [1] 允许本次  [2] 永久允许  [3] 拒绝  : ");
        System.err.flush();

        try {
            // 读一个字符
            int ch = reader.readCharacter();
            
            return switch (ch) {
                case '1' -> HumanDecision.ALLOW_ONCE;      // 允许本次
                case '2' -> HumanDecision.ALLOW_FOREVER;   // 永久允许
                case '3' -> HumanDecision.DENY;            // 拒绝
                default -> HumanDecision.DENY;             // 其他按键默认拒绝
            };
        } catch (Exception e) {
            return HumanDecision.DENY;  // 读取出错，保守拒绝
        }
    }

    // 用户决策
    public enum HumanDecision {
        ALLOW_ONCE,     // 允许本次
        ALLOW_FOREVER,  // 永久允许（写入规则文件）
        DENY            // 拒绝
    }
}
```

### 三个选项详解

| 按键 |   决策   |                      行为                      |
| :--: | :------: | :--------------------------------------------: |
| `1`  | 允许本次 |              这次放行，下次还要问              |
| `2`  | 永久允许 | 这次放行，并且自动写入规则文件，以后都不用问了 |
| `3`  |   拒绝   |      这次拒绝，AI 收到 PERMISSION_DENIED       |

### 永久允许怎么实现？

用户按了 2，要把这条规则写入 `rules.local.yaml`：

```
rules:
  - tool: write_file
    pattern: "pom.xml"
    action: allow
```

**写入哪一层？**

写入 local 层（`.rook/rules.local.yaml`），因为这是用户个人的临时决定，不应该分享给团队。

**为什么要永久允许？**

有些操作用户经常做，比如 "改 pom.xml"，每次都问很烦。

按 2 永久允许，以后就不用问了。

## 第五步：五层串联 — PermissionEngine

把五层串起来，形成完整的权限检查。

```java
// permission/PermissionEngine.java
package com.rook.permission;

import com.rook.tools.ToolCall;
import org.jline.reader.LineReader;
import java.nio.file.Path;

public class PermissionEngine {

    private final Blacklist blacklist;
    private final PathSandbox sandbox;
    private final RuleEngine ruleEngine;
    private final HumanInTheLoop human;
    
    private PermissionMode mode = PermissionMode.DEFAULT;

    public PermissionEngine(Path projectRoot) {
        this.blacklist = new Blacklist();
        this.sandbox = new PathSandbox(projectRoot);
        this.ruleEngine = new RuleEngine(projectRoot);
        this.human = new HumanInTheLoop();
    }

    /**
     * 完整的权限检查：五层串联
     */
    public PermissionResult check(ToolCall call, LineReader reader) {
        
        // ── 第 1 层：黑名单（不可绕过）──
        PermissionResult r1 = blacklist.check(call);
        if (r1.isDenied()) {
            return r1;
        }

        // ── 第 2 层：沙箱（不可绕过）──
        PermissionResult r2 = sandbox.check(call);
        if (r2.isDenied()) {
            return r2;
        }

        // ── 第 3 层：规则引擎 ──
        PermissionResult r3 = ruleEngine.check(call);
        if (r3.isDenied()) {
            return r3;
        }
        // 注意：规则 allow 不直接返回，还要继续检查模式和人在回路
        // 因为规则 allow 只是说"规则不拦"，不代表"一定允许"

        // ── 第 4 层：权限模式 ──
        PermissionVerdict verdict = mode.verdictFor(call.name());
        
        if (verdict == PermissionVerdict.ALLOW) {
            return PermissionResult.allow();
        }
        
        if (verdict == PermissionVerdict.DENY) {
            return PermissionResult.deny("模式禁止: " + call.name(), "mode");
        }

        // ── 第 5 层：人在回路（ASK 时才问）──
        if (verdict == PermissionVerdict.ASK) {
            HumanDecision decision = human.ask(call, "需要用户确认", reader);
            
            return switch (decision) {
                case ALLOW_ONCE -> PermissionResult.allow();
                case ALLOW_FOREVER -> {
                    // 永久允许：写入规则文件
                    addAllowRule(call);
                    yield PermissionResult.allow();
                }
                case DENY -> PermissionResult.deny("用户拒绝", "human");
            };
        }

        // 兜底
        return PermissionResult.deny("未知错误", "unknown");
    }

    /**
     * 切换权限模式
     */
    public void setMode(PermissionMode mode) {
        this.mode = mode;
    }

    public PermissionMode getMode() {
        return mode;
    }

    /**
     * 添加永久允许规则（写入 local 层）
     */

        // 把这条工具+参数写入 rules.local.yaml
        // 具体实现略，就是往 YAML 文件里加一条 allow 规则
    }
}
```

### 五层串联的逻辑

```
工具调用
    │
    ▼
第 1 层：黑名单
    ├─ 拒绝 → 直接返回（不可绕过）
    └─ 通过 ↓
    ▼
第 2 层：沙箱
    ├─ 拒绝 → 直接返回（不可绕过）
    └─ 通过 ↓
    ▼
第 3 层：规则引擎
    ├─ 拒绝 → 直接返回
    └─ 通过/未命中 ↓
    ▼
第 4 层：权限模式
    ├─ ALLOW → 放行
    ├─ DENY → 拒绝
    └─ ASK ↓
    ▼
第 5 层：人在回路
    ├─ 允许本次 → 放行
    ├─ 永久允许 → 写规则 + 放行
    └─ 拒绝 → 拒绝
```

### 为什么规则 allow 不直接返回？

注意这段：

```
PermissionResult r3 = ruleEngine.check(call);
if (r3.isDenied()) {
    return r3;
}
// 规则 allow 不直接返回，继续往下
```

**为什么？**

规则引擎说 allow，只是说 "规则层面不拦你"。

但后面还有模式层和人在回路层，可能还要拦或者要问用户。

**比如：**

- 规则允许 write_file
- 但当前是 PLAN 模式，WRITE 是 DENY
- 那还是要拒绝

所以规则 allow 不直接返回，要继续检查后面的层。

**只有 deny 才直接返回**，因为 deny 是明确的拒绝。

## 完整示例

### 示例 1：默认模式下改文件

```
用户：帮我把 pom.xml 里的 Java 版本改成 21

AI 决定调用 edit_file("pom.xml", ...)
    │
    ▼
权限检查：
  1. 黑名单：不是 exec_command → 通过
  2. 沙箱：pom.xml 在项目内 → 通过
  3. 规则引擎：没命中规则 → 穿透
  4. 权限模式：DEFAULT，WRITE = ASK → 需要问用户
  5. 人在回路：弹窗
     ⚠️  需要确认: 需要用户确认
        工具: edit_file
        参数: {filePath=pom.xml, ...}

**用户按 1：** 允许本次 → 执行成功

**用户按 2：** 永久允许 → 写入规则 → 执行成功 → 以后改 pom.xml 不用问了

**用户按 3：** 拒绝 → AI 收到 PERMISSION_DENIED → AI 调整策略（比如 "那我先告诉你怎么改"）

## 常见坑（详细版）

### 1. 永久允许写 YAML 格式问题

**现象：** Windows 路径写入 YAML 后，反斜杠被当成转义符，路径乱了。

**原因：** YAML 里 `\` 是转义符，`\n` 会被解析成换行。

**比如路径 `C:\Users\project\pom.xml`：**

- 直接写进去 → `C:\Users\project\pom.xml`
- YAML 解析后 → `C:Usersprojectpom.xml`（\U、\p 被转义了）

**解决：** 用单引号包起来，单引号里的内容不转义：

```
rules:
  - tool: write_file
    pattern: 'C:\Users\project\pom.xml'
    action: allow
```

### 2. 模式 Deny 和规则 Deny 的区别

**现象：** 都是拒绝，但原因不一样。

|    来源    |         返回信息          |    layer    |
| :--------: | :-----------------------: | :---------: |
|  模式拒绝  |   "模式禁止: edit_file"   |   `mode`    |
|  规则拒绝  | "规则拒绝: edit_file xxx" |   `rule`    |
| 黑名单拒绝 |      "高危命令: ..."      | `blacklist` |
|  沙箱拒绝  |  "路径超出项目范围: ..."  |  `sandbox`  |
|  用户拒绝  |        "用户拒绝"         |   `human`   |

**为什么要区分？**

- 用户看到拒绝原因，知道是哪一层拦的
- 方便调试：为什么被拦了？
- 可以针对性地调整（模式不对就改模式，规则不对就改规则）

### 3. BYPASS 模式不是万能的

**现象：** 切到 BYPASS 模式，有些操作还是被拦了。

**原因：** BYPASS 只影响第 4 层（模式层），前两层（黑名单 + 沙箱）是硬安全网，任何模式下都生效。

**BYPASS 模式下仍然会被拦的：**

- `rm -rf /` — 黑名单拦
- 读 `/etc/passwd` — 沙箱拦
- 规则里明确 deny 的 — 规则引擎拦

**BYPASS 只是 "模式层全部 ALLOW"，不是 "关闭所有权限检查"。**

### 4. 规则匹配顺序

**现象：** 写了多条规则，预期的那条没生效。

**原因：** 规则按优先级排序，先匹配到的先生效。

**比如：**

```
rules:
  - tool: exec_command
    pattern: "*"
    action: deny        # 先匹配到这条，全部拒绝
    
  - tool: exec_command
    pattern: "git *"
    action: allow       # 这条永远不会生效，因为前面已经 deny 了
```

**解决：** allow 规则要放在 deny 规则前面（高优先级层）。

### 5. 人在回路阻塞 Agent

**现象：** 弹窗确认的时候，Agent 线程卡住了。

**原因：** 权限检查是在 Agent 线程里做的，人在回路要等用户输入，所以 Agent 线程阻塞。

**这是正常的。**

- Agent 等用户确认
- 用户按了键，才继续执行
- 这就是 "人在回路" 的含义

**但要注意：**

- 超时处理：用户太久不回应怎么办？
- 取消处理：用户想取消整个任务怎么办？

### 6. 规则文件热加载

**现象：** 改了 rules.yaml，不生效，要重启程序。

**原因：** RuleEngine 在启动时加载一次规则，之后不重新加载。

**优化方向：**

- 每次 check 都检查文件修改时间
- 或者提供 `:reload-rules` 命令手动重载
- 或者用 WatchService 监听文件变化

### 7. glob 匹配的边界情况

**现象：** 有些 pattern 匹配结果不符合预期。

**常见问题：**

- ```
  *.java
  ```

   不匹配 

  ```
  src/Main.java
  ```

  （因为 

  ```
  *
  ```

   不跨目录）

  - 要用 `**/*.java`

- ```
  git *
  ```

   不匹配 

  ```
  git
  ```

  （没有参数）

  - 可以用 `git*` 或者加一条无 pattern 的规则

- 大小写敏感：

  ```
  *.JAVA
  ```

   不匹配 

  ```
  Main.java
  ```

  - 可以转成小写再匹配

## 权限五层总结

| 层级 |      名称      |       作用       |   可配置   |    可绕过    |
| :--: | :------------: | :--------------: | :--------: | :----------: |
|  1   |   Blacklist    |   高危命令拦截   |   ❌ 内置   |  ❌ 不可绕过  |
|  2   |  PathSandbox   | 路径限制在项目内 |   ❌ 内置   |  ❌ 不可绕过  |
|  3   |   RuleEngine   |  用户自定义规则  |   ✅ YAML   | ✅ 可以改规则 |
|  4   | PermissionMode |   全局模式切换   |   ✅ 四档   | ✅ 可以切模式 |
|  5   | HumanInTheLoop |     用户确认     | ✅ 每次决定 |  ✅ 用户允许  |

**前两层是硬安全网，后三层是灵活控制。**
