# 27 — 扩展指南

## 这一章做什么

教会别人如何在 Rook 上扩展 ——**加新工具、新 Provider、新 Skill、新 Hook**。四种扩展方式，每种一个完整例子，从创建到验证全流程。

**读完这一章你能做到：**

- 给 Rook 加一个自定义工具（比如查天气、调内部 API）
- 接入一个新的 LLM 供应商（比如智谱 GLM、通义千问）
- 写一个可复用的 Skill（比如部署、代码格式化）
- 配置一个 Hook 规则（比如提交前自动跑测试）

## 扩展方式总览

Rook 有四种扩展方式，按 "改动量从小到大" 排列：

表格







|    方式     |       改什么        | 编译 |         适用场景         | 难度  |
| :---------: | :-----------------: | :--: | :----------------------: | :---: |
|   加 Hook   |    写 YAML 配置     | 不用 | 自动化策略、生命周期钩子 | ★☆☆☆☆ |
|  加 Skill   | 放 SKILL.md 到目录  | 不用 |  可复用的操作流程、SOP   | ★★☆☆☆ |
|   加 Tool   | 新建 Java 类 + 注册 |  要  |   新能力、新 API 接入    | ★★★☆☆ |
| 加 Provider | 新建 Java 类 + 工厂 |  要  |     新 LLM 模型接入      | ★★★★☆ |

**选择建议：**

- 只是想在某个时机自动执行点什么 → **Hook**
- 有一套固定操作流程想复用 → **Skill**
- 需要调用外部 API 或执行特定逻辑 → **Tool**
- 想接一个新的大模型 → **Provider**

## 一、加一个新工具（Tool）

### 什么时候需要加 Tool

- 需要调用外部 API（天气、数据库、内部服务）
- 需要执行特定的业务逻辑
- 内置工具不够用（比如需要调用公司内部接口）
- 需要把复杂操作封装成一个工具给 AI 用

### 完整例子：天气查询工具

#### 第 1 步：创建 Tool 类

java



运行





```
// tools/impl/WeatherTool.java
package com.rook.tools.impl;

import com.rook.tools.Tool;
import com.rook.tools.ToolResult;

import java.net.URI;
import java.net.http.HttpClient;
import java.net.http.HttpRequest;
import java.net.http.HttpResponse;
import java.time.Duration;
import java.util.List;
import java.util.Map;

import com.fasterxml.jackson.databind.JsonNode;
import com.fasterxml.jackson.databind.ObjectMapper;

public class WeatherTool implements Tool {

    private static final ObjectMapper MAPPER = new ObjectMapper();
    private static final HttpClient HTTP = HttpClient.newBuilder()
        .connectTimeout(Duration.ofSeconds(5))
        .build();

    // 免费天气 API（示例，实际用你自己的）
    private static final String API_URL = 
        "https://api.example.com/weather?city=%s&key=%s";

    @Override
    public String name() {
        return "get_weather";
    }

    @Override
    public String description() {
        return "查询指定城市的当前天气信息，包括温度、天气状况、湿度、风力。"
            + "当用户询问天气、气温、是否下雨时使用此工具。"
            + "参数: city（城市名，如'北京'、'上海'）";
    }

    @Override
    public Map<String, Object> inputSchema() {
        return Map.of(
            "type", "object",
            "properties", Map.of(
                "city", Map.of(
                    "type", "string",
                    "description", "城市名称，如'北京'、'武汉'、'上海'"
                )
            ),
            "required", List.of("city")
        );
    }

    @Override
    public ToolResult execute(Map<String, Object> params) {
        // 1. 提取参数
        String city = (String) params.get("city");
        if (city == null || city.isBlank()) {
            return ToolResult.error("city 参数不能为空");
        }

        // 2. 从环境变量读 API Key（不要硬编码）
        String apiKey = System.getenv("WEATHER_API_KEY");
        if (apiKey == null || apiKey.isBlank()) {
            return ToolResult.error("未配置 WEATHER_API_KEY 环境变量");
        }

        try {
            // 3. 构建请求
            String url = String.format(API_URL, 
                java.net.URLEncoder.encode(city, "UTF-8"), apiKey);
            
            HttpRequest request = HttpRequest.newBuilder()
                .uri(URI.create(url))
                .timeout(Duration.ofSeconds(10))
                .GET()
                .build();

            // 4. 发送请求
            HttpResponse<String> response = HTTP.send(request, 
                HttpResponse.BodyHandlers.ofString());

            // 5. 检查状态码
            if (response.statusCode() != 200) {
                return ToolResult.error("天气 API 返回错误: HTTP " 
                    + response.statusCode());
            }

            // 6. 解析响应
            JsonNode json = MAPPER.readTree(response.body());
            String weather = json.path("weather").asText("未知");
            int temp = json.path("temperature").asInt(0);
            int humidity = json.path("humidity").asInt(0);
            String wind = json.path("wind").asText("未知");

            // 7. 格式化结果
            String result = String.format(
                "【%s 天气】\n" +
                "天气状况: %s\n" +
                "温度: %d°C\n" +
                "湿度: %d%%\n" +
                "风力: %s",
                city, weather, temp, humidity, wind
            );

            return ToolResult.ok(result);

        } catch (Exception e) {
            // 8. 异常处理：不要抛异常，返回错误结果
            return ToolResult.error("查询天气失败: " + e.getMessage());
        }
    }
}
```

#### 逐段详解

**① name () — 工具名**

java



运行





```
public String name() { return "get_weather"; }
```

- 命名规范：小写 + 下划线，动词 + 名词
- 要简短但能表达含义
- AI 看到这个名字会判断什么时候用

**② description () — 工具描述**

java



运行





```
public String description() {
    return "查询指定城市的当前天气信息...当用户询问天气时使用...";
}
```

- **这是 AI 选不选这个工具的关键**
- 要写清楚：做什么、什么时候用、参数含义
- 写得好，AI 就会在正确的时机调用
- 写得差，AI 可能不知道什么时候用，或者用错

**③ inputSchema () — 参数 Schema**

java



运行





```
return Map.of(
    "type", "object",
    "properties", Map.of(
        "city", Map.of("type", "string", "description", "...")
    ),
    "required", List.of("city")
);
```

- JSON Schema 格式，告诉 AI 参数长什么样
- 每个参数都要有 description
- required 列出必填参数
- AI 会根据这个 Schema 自动填参数

**④ execute () — 执行逻辑**

java



运行





```
public ToolResult execute(Map<String, Object> params) {
    String city = (String) params.get("city");
    // ... 业务逻辑 ...
    return ToolResult.ok(result);
}
```

- 入参是 Map，AI 传的参数都在这里
- **永远不要抛异常**， catch 住返回 `ToolResult.error()`
- 成功返回 `ToolResult.ok(content)`
- 失败返回 `ToolResult.error(reason)`

**⑤ API Key 从环境变量读**

java



运行





```

```

- 不要硬编码密钥到代码里
- 用环境变量，安全且灵活
- 没配置时返回友好的错误提示

### Tool 开发的最佳实践

#### 1. 描述写好是关键

**差的描述：**

java



运行





```
return "获取天气";
```

AI 不知道什么时候用，参数要传什么。

**好的描述：**

java



运行





```
return "查询指定城市的当前天气信息，包括温度、天气状况、湿度。"
    + "当用户询问天气、气温、是否下雨、穿什么衣服时使用。"
    + "参数: city（城市名，如'北京'）";
```

AI 一看就知道：用户问天气 → 用这个工具，传 city 参数。

#### 2. 参数要校验

java



运行





```
String city = (String) params.get("city");
if (city == null || city.isBlank()) {
    return ToolResult.error("city 参数不能为空");
}
```

AI 可能传错参数（比如传了空字符串、传了数字），要校验。

#### 3. 永远不要抛异常

java



运行





```
try {
    // 业务逻辑
} catch (Exception e) {
    return ToolResult.error("失败: " + e.getMessage());
}
```

- 抛异常会导致整个 AgentLoop 崩溃
- 应该 catch 住，返回错误结果
- AI 看到错误结果会调整策略（比如换个方式、或者告诉用户）

#### 4. 超时控制

java



运行





```
HttpClient HTTP = HttpClient.newBuilder()
    .connectTimeout(Duration.ofSeconds(5))
    .build();

request = HttpRequest.newBuilder()
    .timeout(Duration.ofSeconds(10))
    .build();
```

- 外部 API 可能很慢，要设超时
- 连接超时 5 秒，请求超时 10 秒
- 超时了返回错误，不要让用户一直等

#### 5. 结果要格式化

java



运行





```
String result = String.format(
    "【%s 天气】\n温度: %d°C\n湿度: %d%%",
    city, temp, humidity
);
```

- 返回给 AI 的结果要清晰、结构化
- AI 更容易理解，也更容易转述给用户
- 不要返回原始 JSON，要格式化成人能看懂的

### 常见坑

#### 坑 1：工具名和已有工具冲突

**现象：** 注册了 `read_file`，但内置工具已经有了。

**原因：** ToolRegistry 用 Map 存储，同名会覆盖。

**解决：**

- 用独特的名字，比如 `get_weather` 而不是 `weather`
- 注册前检查是否已存在
- 或者允许覆盖（但要知道自己在做什么）

#### 坑 2：Schema 写错导致 AI 不会填参

**现象：** AI 调用工具时参数为空，或者参数名不对。

**原因：** inputSchema 格式不对，或者 description 没写清楚。

**解决：**

- 严格按照 JSON Schema 格式
- 每个参数都要有 description
- required 列出必填参数
- 可以打印工具定义，检查 AI 看到的是什么

#### 坑 3：返回结果太大，超 token

**现象：** 工具返回了一大堆数据，上下文爆炸。

**原因：** 没有截断，直接返回原始响应。

**解决：**

- 截断到合理长度（比如 2000 字符）
- 只返回 AI 需要的字段
- 太大的结果存盘，返回文件路径（参考第 15 章 ToolResultStorage）

#### 坑 4：有副作用的工具没确认

**现象：** AI 自动调用了 "删除数据库" 的工具，把数据删了。

**原因：** 危险工具没有权限保护。

**解决：**

- 危险操作（删除、修改、发送）应该走权限确认
- 或者在 description 里明确标注 "危险操作"
- 配合 PermissionEngine 的规则引擎限制

## 二、加一个新 Provider（LLM 供应商）

### 什么时候需要加 Provider

- 想接入一个新的大模型（智谱 GLM、通义千问、文心一言等）
- 现有 Provider 不支持某个模型的特殊功能
- 想用公司内部部署的模型

### 前提：了解目标 API

加 Provider 之前，先搞清楚目标 API 的：

- 端点 URL
- 认证方式（Bearer Token? API Key?）
- 请求体格式
- 响应格式（JSON? SSE 流式？）
- 工具调用格式（如果支持）

### 完整例子：智谱 GLM Provider

#### 第 1 步：创建 Provider 类

java



运行





```
// llm/GlmProvider.java
package com.rook.llm;

import com.fasterxml.jackson.databind.JsonNode;
import com.fasterxml.jackson.databind.ObjectMapper;

import java.net.URI;
import java.net.http.HttpClient;
import java.net.http.HttpRequest;
import java.net.http.HttpResponse;
import java.time.Duration;
import java.util.*;

public class GlmProvider implements LlmProvider {

    private static final ObjectMapper MAPPER = new ObjectMapper();
    private static final HttpClient HTTP = HttpClient.newBuilder()
        .connectTimeout(Duration.ofSeconds(10))
        .build();

    private final ProviderConfig config;

    public GlmProvider(ProviderConfig config) {
        this.config = config;
    }

    @Override
    public String name() {
        return config.name();
    }

    @Override
    public void stream(List<ChatMessage> messages, 
                       List<ToolDef> tools,
                       StreamCallback callback) {
        try {
            // 1. 构建请求体
            Map<String, Object> body = new LinkedHashMap<>();
            body.put("model", config.model());
            body.put("stream", true);
            body.put("messages", toGlmMessages(messages));
            
            // 工具调用（如果支持）
            if (tools != null && !tools.isEmpty()) {
                body.put("tools", toGlmTools(tools));
                body.put("tool_choice", "auto");
            }

            // 2. 构建 HTTP 请求
            HttpRequest request = HttpRequest.newBuilder()
                .uri(URI.create(config.baseUrl() + "/chat/completions"))
                .header("Authorization", "Bearer " + config.apiKey())
                .header("Content-Type", "application/json")
                .POST(BodyPublishers.ofString(
                    MAPPER.writeValueAsString(body), 
                    java.nio.charset.StandardCharsets.UTF_8
                ))
                .build();

            // 3. 发送请求
            HttpResponse<java.io.InputStream> response = HTTP.send(request,
                HttpResponse.BodyHandlers.ofInputStream());

            if (response.statusCode() != 200) {
                String errorBody = new String(response.body().readAllBytes());
                throw new LlmException("GLM API 错误: HTTP " 
                    + response.statusCode() + " - " + errorBody);
            }

            // 4. 解析 SSE 流
            try (java.io.BufferedReader reader = new java.io.BufferedReader(
                    new java.io.InputStreamReader(response.body(), 
                        java.nio.charset.StandardCharsets.UTF_8))) {
                
                String line;
                while ((line = reader.readLine()) != null) {
                    if (!line.startsWith("data: ")) continue;
                    
                    String data = line.substring(6);
                    if ("[DONE]".equals(data)) break;

                    JsonNode event = MAPPER.readTree(data);
                    
                    // 5. 提取增量内容
                    JsonNode choices = event.path("choices");
                    if (choices.isArray() && choices.size() > 0) {
                        JsonNode delta = choices.get(0).path("delta");
                        
                        // 文本增量
                        String content = delta.path("content").asText(null);
                        if (content != null) {
                            callback.onToken(content);
                        }
                        
                        // 工具调用增量（如果有）
                        JsonNode toolCalls = delta.path("tool_calls");
                        if (toolCalls.isArray() && toolCalls.size() > 0) {
                            // 解析工具调用...
                            // 不同 API 格式可能不同，需要适配
                        }
                    }
                }
            }

            callback.onComplete();

        } catch (LlmException e) {
            callback.onError(e);
        } catch (Exception e) {
            callback.onError(new LlmException("GLM 调用失败: " + e.getMessage(), e));
        }
    }

    /**
     * 把 Rook 的 ChatMessage 转成 GLM 格式
     */
    private List<Map<String, Object>> toGlmMessages(List<ChatMessage> messages) {
        List<Map<String, Object>> result = new ArrayList<>();
        for (ChatMessage msg : messages) {
            Map<String, Object> glmMsg = new LinkedHashMap<>();
            glmMsg.put("role", msg.role());  // user/assistant/system
            
            // 文本内容
            if (msg.content() instanceof String) {
                glmMsg.put("content", msg.content());
            } else {
                // 多模态内容（工具结果等），需要转成对应格式
                glmMsg.put("content", msg.content().toString());
            }
            
            result.add(glmMsg);
        }
        return result;
    }

    /**
     * 把 Rook 的 ToolDef 转成 GLM 格式
     */
    private List<Map<String, Object>> toGlmTools(List<ToolDef> tools) {
        List<Map<String, Object>> result = new ArrayList<>();
        for (ToolDef tool : tools) {
            Map<String, Object> glmTool = new LinkedHashMap<>();
            glmTool.put("type", "function");
            glmTool.put("function", Map.of(
                "name", tool.name(),
                "description", tool.description(),
                "parameters", tool.inputSchema()
            ));
            result.add(glmTool);
        }
        return result;
    }
}
```

// llm/ProviderFactory.java
public class ProviderFactory {
    public static Map<String, LlmProvider> create(AppConfig config) {
        Map<String, LlmProvider> providers = new LinkedHashMap<>();
        for (ProviderConfig pc : config.providers()) {
            LlmProvider p = switch (pc.protocol().toLowerCase()) {
                case "anthropic" -> new AnthropicProvider(pc);
                case "openai" -> new OpenAiProvider(pc);
                case "glm" -> new GlmProvider(pc);  // ★ 加这一行
                default -> throw new IllegalArgumentException(
                    "未知协议: " + pc.protocol());
            };
            providers.put(pc.name(), p);
        }
        return providers;
    }
}
```

### Provider 开发的注意事项

#### 1. 消息格式转换

每个 API 的消息格式可能略有不同：

- OpenAI 兼容：`{role, content}`，简单
- Anthropic：`{role, content}`，但 content 可以是数组（多模态）
- 有些不支持 system role，要转成 user 消息

**要写一个 `toXxxMessages()` 方法做转换。**

#### 2. 工具调用格式

工具调用的格式差异更大：

- OpenAI 兼容：`tools: [{type: "function", function: {name, description, parameters}}]`
- Anthropic：`tools: [{name, description, input_schema}]`
- 有些模型不支持工具调用，要降级（只聊天）

**如果目标 API 不支持工具调用，这个 Provider 就不能用于 AgentLoop（只能聊天）。**

#### 3. 流式 vs 非流式

- 流式（SSE）：体验好，token 一个个出来
- 非流式：等全部返回再一次性输出

**Rook 的 AgentLoop 用的是流式，所以 Provider 必须实现 stream ()。**

如果目标 API 只有非流式接口，可以在 stream () 里调用非流式，然后一次性回调。

#### 4. 错误处理

java



运行





```
if (response.statusCode() != 200) {
    String errorBody = new String(response.body().readAllBytes());
    throw new LlmException("API 错误: HTTP " + response.statusCode());
}
```

- 401：API Key 错了
- 429：限流了
- 500：服务器挂了
- 都要给出清晰的错误信息

#### 5. 超时和重试

java



运行





```
HttpClient HTTP = HttpClient.newBuilder()
    .connectTimeout(Duration.ofSeconds(10))
    .build();
```

- 连接超时、请求超时都要设
- 可以加重试（网络错误时重试 2-3 次）
- 但 401、400 这种不要重试（重试也没用）

### 常见坑

#### 坑 1：协议名和配置不匹配

**现象：** 配置里写 `protocol: glm`，但 ProviderFactory 里没加 case。

**原因：** 忘记在工厂里加分支。

**解决：** 加 case，或者用更通用的 `openai-compat` 协议（所有 OpenAI 兼容的都用同一个 Provider）。

#### 坑 2：base_url 末尾斜杠

**现象：** 请求 URL 变成 `https://api.xxx/v1//chat/completions`（双斜杠）。

**原因：** base_url 末尾带了 `/`，代码里又拼了 `/chat/completions`。

**解决：**

- 配置里 base_url 不要带末尾斜杠
- 或者代码里做归一化（去掉末尾斜杠）

#### 坑 3：SSE 解析漏了心跳

**现象：** 有些 API 会发心跳行（`: keepalive` 或空行），解析报错。

**原因：** 只处理了 `data: ` 开头的行，其他行没跳过。

**解决：**

java



运行





```
if (!line.startsWith("data: ")) continue;  // 跳过心跳、空行等
```

#### 坑 4：工具调用格式不兼容

**现象：** AI 返回了工具调用，但解析不出来。

**原因：** 不同 API 的工具调用格式不同。

**解决：**

- 仔细看目标 API 的文档
- 工具调用可能在 `choices[0].message.tool_calls`（非流式）
- 或 `choices[0].delta.tool_calls`（流式增量）
- 增量可能是分片的，要累积

## 三、加一个新 Skill

### 什么时候需要加 Skill

- 有一套固定的操作流程，想反复使用
- 想把某个领域的最佳实践固化下来
- 想给 AI 一个专门的 "专家模式"
- 不想每次都重复说同样的指令

### Skill 和 Tool 的区别

表格







| 维度 |          Tool           |             Skill             |
| :--: | :---------------------: | :---------------------------: |
| 本质 | Java 代码，执行具体操作 | Markdown 指令，指导 AI 怎么做 |
| 编译 |          需要           |            不需要             |
| 能力 | 能调 API、执行业务逻辑  | 只能用已有工具，不能加新能力  |
| 适用 |    新能力、外部接口     |    操作流程、SOP、专家模式    |
| 例子 |    查天气、查数据库     |    代码审查、部署、写测试     |

**简单说：Tool 是 "手"，Skill 是 "脑子"。**

- Tool 给 AI 新的手（能做新的事）
- Skill 给 AI 新的脑子（知道怎么做某件事）

#### 第 1 步：创建 Skill 目录

   - 进程状态

- 不要在部署过程中修改源代码
- 不要跳过测试，除非用户明确要求 `-DskipTests`
- 每一步失败都要停下来，不要继续下一步
- 所有命令执行前，先告诉用户要执行什么
```

### Skill 开发的最佳实践

#### 1. 描述写清楚

**差的描述：**

```
description: "部署"
```

用户和 AI 都不知道这个 Skill 具体做什么。

**好的描述：**

```
description: "将项目打包并部署到远程服务器，包括构建、上传、重启全流程"
```

一看就知道：做部署，包含构建 + 上传 + 重启。

#### 2. 工具白名单要精准

```
allowed_tools: [exec_command, read_file, glob, grep]
```

- 只给需要的工具，不要给太多
- 部署不需要 write_file，就别给
- 防止 AI 在部署过程中乱改文件
- 也能提高 AI 选对工具的概率

#### 3. 流程要分步，每步有检查点

```
## 构建

   - 如果构建失败，把错误信息展示给用户，停止部署
```

- 每一步都要有成功 / 失败的处理
- 失败了要停下来，不要硬着头皮继续
- 告诉用户当前进度

#### 4. 考虑异常情况

```
- 上传失败要重试一次
- 重试还失败就告诉用户
```

- 网络可能断、命令可能失败
- 写清楚遇到异常怎么办
- AI 遇到异常就知道怎么处理，不用瞎猜

### 常见坑

#### 坑 1：Skill 没生效

**现象：** 写了 SKILL.md，但 `/deploy` 命令不存在。

**原因：**

- 放错目录了（应该是 `.rook/skills/deploy/SKILL.md`）
- 文件名大小写不对（必须是 SKILL.md，不是 skill.md）
- 没重启（Skill 启动时加载）

**解决：**

- 检查目录结构：`.rook/skills/<name>/SKILL.md`
- 重启 Rook
- 看启动日志有没有 "[Skill] 已加载: deploy"

#### 坑 2：AI 不按 Skill 流程走

**现象：** 用了 /deploy，但 AI 没按写的步骤来。

**原因：**

- SKILL.md 写得太模糊
- 或者 AI 模型太弱，理解不了复杂流程

**解决：**

- 步骤写得更具体、更明确
- 每一步都写清楚 "做什么"、"怎么做"、"失败了怎么办"
- 用强模型（比如 Claude Sonnet）执行复杂 Skill

#### 坑 3：allowed_tools 限制太死

**现象：** Skill 执行到一半，发现需要某个工具但不在白名单里。

**原因：** 白名单没列全。

**解决：**

- 仔细想清楚整个流程需要哪些工具
- 可以先不设白名单（空列表表示不限制），跑通了再加
- 或者给常用工具（read_file, exec_command）总是放开

#### 坑 4：Skill 之间名字冲突

**现象：** 项目级 Skill 和用户级 Skill 同名。

**原因：** 三级加载（内置 < 用户 < 项目），后者覆盖前者。

**解决：**

- 这是设计如此，优先级高的覆盖低的
- 如果不想被覆盖，改个名字
- 可以用 /skills 命令查看所有已加载的 Skill

## 四、加一个新 Hook

### 什么时候需要加 Hook

- 想在某个时机自动执行点什么（比如任务完成后发通知）
- 想加自定义的安全策略（比如禁止修改某些文件）
- 想集成外部系统（比如提交前自动跑 CI）
- 想在 LLM 调用前注入提示词

### Hook 和 Skill 的区别

|   维度   |              Hook               |        Skill        |
| :------: | :-----------------------------: | :-----------------: |
| 触发方式 |        自动（事件驱动）         | 手动（/skill 命令） |
|   时机   | 生命周期事件（PRE_TOOL_USE 等） |     用户调用时      |
|   作用   |    拦截、通知、注入、自动化     |  指导 AI 完成任务   |
|   例子   |  工具执行前检查、完成后发通知   |   代码审查、部署    |

**简单说：Skill 是用户主动调用的，Hook 是自动触发的。**

### 完整例子：提交前自动跑测试

#### 第 1 步：写 hooks.yaml

```
# .rook/hooks.yaml
hooks:
  # Hook 1：执行 git commit 前自动跑测试
  - name: test-before-commit
    description: "执行 git commit 前自动运行单元测试，测试失败则拦截"
    event: PRE_TOOL_USE
    if:
      all_of:
        - tool: exec_command
        - input_regex: "git\\s+commit"
    action:
      type: command
      command: "mvn test -q"
      timeout: 120
    async: false  # 必须同步，因为要拦截

  # Hook 2：Agent 任务完成后发桌面通知
  - name: notify-on-complete
    description: "Agent 任务完成时发送桌面通知"
    event: SESSION_END
    action:
      type: command
      command: "notify-send 'Rook' '任务完成'"
    async: true  # 异步，不阻塞

  # Hook 3：修改 pom.xml 前提醒
  - name: warn-on-pom-edit
    description: "修改 pom.xml 时提醒用户确认依赖变更"
    event: PRE_TOOL_USE
    if:
      all_of:
        - tool: edit_file
        - input_glob: "**/pom.xml"
    action:
      type: prompt
      inject: "注意：你正在修改 pom.xml，这可能影响依赖和构建。请确认修改内容。"
    async: false

  # Hook 4：工具执行失败时上报
  - name: report-tool-error
    description: "工具执行失败时上报到监控系统"
    event: TOOL_ERROR
    action:
      type: http
      url: "https://monitor.example.com/api/errors"
      method: POST
      headers:
        Content-Type: "application/json"
      body: |
        {
          "tool": "${ROOK_TOOL}",
          "error": "${ROOK_ERROR}",
          "session": "${ROOK_SESSION_ID}"
        }
    async: true
```

#### 逐段详解

**① 基本结构**

```
hooks:
  - name: test-before-commit
    description: "..."
    event: PRE_TOOL_USE
    if: ...
    action: ...
    async: false
```

|    字段     |             含义             |      必填      |
| :---------: | :--------------------------: | :------------: |
|    name     |      Hook 名，唯一标识       |       是       |
| description |             描述             |       否       |
|    event    |      触发事件（11 种）       |       是       |
|     if      |  匹配条件（不写就匹配所有）  |       否       |
|   action    |          执行的动作          |       是       |
|    async    | 是否异步（拦截类必须 false） | 否，默认 false |

**② 事件类型（11 种）**

|        事件        |      触发时机       | 可拦截 |
| :----------------: | :-----------------: | :----: |
|   SESSION_START    |      会话开始       |   否   |
|    SESSION_END     |      会话结束       |   否   |
|    ROUND_START     | 每轮 AgentLoop 开始 |   否   |
|     ROUND_END      |      每轮结束       |   否   |
|    PRE_LLM_CALL    |      调 LLM 前      |   是   |
|   POST_LLM_CALL    |      调 LLM 后      |   否   |
|    PRE_TOOL_USE    |     工具执行前      |   是   |
|   POST_TOOL_USE    |     工具执行后      |   否   |
| USER_PROMPT_SUBMIT |   用户提交消息时    |   是   |
|     TOOL_ERROR     |    工具执行出错     |   否   |
|    COMPRESSION     |    上下文压缩时     |   否   |

**③ 条件匹配（if）**

```
if:
  all_of:
    - tool: exec_command
    - input_regex: "git\\s+commit"
```

四种匹配模式：

- `tool: xxx`：工具名精确匹配
- `input_regex: xxx`：工具输入正则匹配
- `input_glob: xxx`：工具输入通配符匹配
- `not: {tool: xxx}`：不等于

逻辑组合：

- `all_of: [...]`：所有条件都满足（AND）
- `any_of: [...]`：任一条件满足（OR）
- 支持嵌套

**④ 动作类型（action）**

四种动作：

**command：执行 shell 命令**

```
action:
  type: command
  command: "mvn test -q"
  timeout: 120
```

- exit code 0 = 放行
- exit code 2 = 拦截（stderr 为拒绝原因）
- 其他 code = 执行失败，不拦截

**prompt：注入提示词**

```
action:
  type: prompt
  inject: "注意：你正在修改 pom.xml..."
```

- 把提示词注入到对话中
- AI 下一轮会看到

**http：发 HTTP 请求**

```
action:
  type: http
  url: "https://monitor.example.com/api/errors"
  method: POST
  headers:
    Content-Type: "application/json"
  body: |
    {"tool": "${ROOK_TOOL}"}
```

- 常用于 webhook 通知、上报
- 不拦截，只通知

**subagent：调子 Agent**

```
action:
  type: subagent
  agent_type: review
  prompt: "审查刚才的改动"
```

- 预留扩展，后续版本支持

**⑤ 环境变量注入**

动作执行时，这些环境变量可用：

- `ROOK_EVENT`：事件名
- `ROOK_TOOL`：工具名
- `ROOK_TOOL_INPUT`：工具输入（JSON）
- `ROOK_TOOL_RESULT`：工具结果
- `ROOK_ERROR`：错误信息
- `ROOK_SESSION_ID`：会话 ID
- `ROOK_WORKING_DIR`：工作目录

#### 第 2 步：放到正确位置

Hook 配置文件有三级（优先级从高到低）：

1. `./.rook/hooks.local.yaml` — 项目本地，不提交 git（最高）
2. `./.rook/hooks.yaml` — 项目共享，可提交 git
3. `~/.rook/hooks.yaml` — 用户全局（最低）

**这个例子放项目级：** `./.rook/hooks.yaml`

#### 第 3 步：重启验证

```

```

```

[调用工具: exec_command]
  command: git commit -m "xxx"

[Hook: test-before-commit] 执行 mvn test -q...
[OK] 测试通过

[OK] 提交成功
```

**如果测试失败：**

```

```

### Hook 开发的最佳实践

#### 1. 拦截类 Hook 必须同步

```
async: false
```

- PRE_TOOL_USE、USER_PROMPT_SUBMIT、PRE_LLM_CALL 是可拦截事件
- 这些事件的 Hook 必须同步执行（async: false）
- 异步的话，工具都执行完了才拦截，没意义
- HookEngine 加载时会校验，违反直接抛异常

#### 2. 命令退出码约定

```
# 放行
exit 0

# 拦截
echo "测试失败，不能提交" >&2
exit 2
```

- 0 = 成功，放行
- 2 = 拦截，stderr 是拒绝原因
- 其他 = 执行失败，不拦截（记日志）

#### 3. 条件写精准

```
# 差：所有 exec_command 都跑测试
if:
  tool: exec_command

# 好：只有 git commit 才跑测试
if:
  all_of:
    - tool: exec_command
    - input_regex: "git\\s+commit"
```

- 条件太宽会导致 Hook 频繁触发，影响性能
- 写精准，只在需要的时候触发

#### 4. 异步 Hook 不阻塞

```
# 通知类用异步
- name: notify-on-complete
  event: SESSION_END
  action:
    type: command
    command: "notify-send ..."
  async: true  # 不阻塞
```

- 通知、上报类的用异步
- 用户不用等它执行完
- 拦截、检查类的用同步

### 常见坑

#### 坑 1：Hook 没触发

**现象：** 写了 Hook，但没生效。

**原因：**

- 放错文件了（应该是 `.rook/hooks.yaml`）
- event 名写错了（大小写、拼写）
- 条件不匹配
- 没重启

**解决：**

- 检查文件路径和文件名
- 对照事件列表检查 event 名
- 把 if 去掉，看能不能触发（排除条件问题）
- 重启 Rook，看启动日志

#### 坑 2：拦截不生效

**现象：** Hook 执行了，但没拦住。

**原因：**

- async: true（异步不拦截）
- 命令 exit code 不是 2
- 事件不可拦截（比如 POST_TOOL_USE 不能拦截）

**解决：**

- 拦截类 Hook 必须 async: false
- 命令拦截时 `exit 2`，拒绝原因写 stderr
- 只有 PRE_ 开头的事件能拦截

#### 坑 3：正则转义问题

**现象：** `input_regex: "git\s+commit"` 不匹配。

**原因：** YAML 里 `\s` 被当成转义，正则里需要 `\\s`。

**解决：**

```
input_regex: "git\\s+commit"  # 双反斜杠
```

- YAML 字符串里的反斜杠要转义
- 或者用单引号：`input_regex: 'git\s+commit'`（单引号不转义）

#### 坑 4：Hook 执行超时

**现象：** Hook 命令跑太久，卡住了。

**原因：** 没设超时，或者超时太长。

**解决：**

```
action:
  type: command
  command: "mvn test"
  timeout: 120  # 2 分钟超时
```

- 给 command 动作设 timeout
- 超时后 Hook 失败，不拦截（同步）或记日志（异步）

#### 坑 5：Hook 自身失败影响主流程

**现象：** Hook 报错了，AgentLoop 也崩了。

**原因：** 早期版本没处理 Hook 异常。

**解决：**

- HookEngine 会 catch Hook 执行的异常
- 记日志，返回 ok（不拦截）
- Hook 自身失败不应该影响主流程
- 如果影响了，是 bug，检查 HookEngine 的实现

## 四种扩展方式总结

|      方式       |       改什么        | 编译 | 难度  |         适用场景         |             例子             |
| :-------------: | :-----------------: | :--: | :---: | :----------------------: | :--------------------------: |
|   **加 Hook**   |    写 YAML 配置     | 不用 | ★☆☆☆☆ | 自动化策略、生命周期钩子 |   提交前跑测试、完成后通知   |
|  **加 Skill**   | 放 SKILL.md 到目录  | 不用 | ★★☆☆☆ |  可复用的操作流程、SOP   |    部署、代码审查、写测试    |
|   **加 Tool**   | 新建 Java 类 + 注册 |  要  | ★★★☆☆ |  新能力、外部 API 接入   | 查天气、查数据库、调内部接口 |
| **加 Provider** | 新建 Java 类 + 工厂 |  要  | ★★★★☆ |     新 LLM 模型接入      | 智谱 GLM、通义千问、文心一言 |

### 扩展优先级建议

**先想清楚需求，再选扩展方式：**

1. **只是想在某个时机自动做点什么？** → Hook
   - 例：每次工具执行前检查、完成后发通知
   - 不用写代码，配置就行
2. **有一套固定流程想反复用？** → Skill
   - 例：部署、代码审查、重构 SOP
   - 写 Markdown，不用编译
3. **需要新的能力（调 API、执行业务逻辑）？** → Tool
   - 例：查天气、查数据库、发邮件
   - 写 Java 代码，编译
4. **想接一个新的大模型？** → Provider
   - 例：智谱 GLM、通义千问
   - 写 Java 代码，适配 API 格式

### 扩展的通用原则

1. **优先用配置，其次用代码**
   - 能 Hook/Skill 解决的，就别写 Tool
   - 配置灵活，改了不用编译
2. **面向接口编程**
   - Tool 实现 `Tool` 接口
   - Provider 实现 `LlmProvider` 接口
   - 符合接口就能插拔
3. **注册中心模式**
   - ToolRegistry、ProviderFactory、SkillRegistry
   - 加新的只要注册一下，不用改核心逻辑
4. **错误友好**
   - Tool 不抛异常，返回 ToolResult.error ()
   - Provider 抛 LlmException，带清晰错误信息
   - Hook 失败不影响主流程
5. **安全第一**
   - 危险工具走权限确认
   - API Key 用环境变量，不硬编码
   - Hook 拦截类必须同步
