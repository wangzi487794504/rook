# 26 — 完整流程走查

## 这一章做什么

用一条真实请求 **"把 pom.xml 的 Java 版本从 11 改成 17"**，从头到尾走一遍 Rook 的所有模块调用链。

**目标：** 让你看到用户输入一句话后，背后 10 个包、几十个类是怎么协作的。

## 用户输入

```
把 pom.xml 的 Java 版本从 11 改成 17
```

**用户看到的：**

```
> 把 pom.xml 的 Java 版本从 11 改成 17
< 我来帮你修改 pom.xml 中的 Java 版本。

[调用工具: edit_file]
  文件: pom.xml
  替换: <java.version>11</java.version> → <java.version>17</java.version>
[OK]

< 已将 pom.xml 中的 Java 版本从 11 改为 17。你可以运行 `mvn compile` 验证一下。
>
```

**背后发生的：** 10 个包、几十个类、两次 LLM 调用、一次工具执行、一次权限确认。

public void start() {
    while (running) {
        String input = reader.readLine("> ");  // 打印提示符，等待输入
        
        if (input == null) { break; }  // Ctrl+D 退出
        input = input.strip();

        // 多行输入检测（第4章）

        }

        // 分流：斜杠命令 vs 普通对话

            if (feedText != null) {
                processMessage(feedText);
            }

        }
    }
}

### 第 2 步：processMessage — 保存消息 + 启动 AgentLoop

```
// cli/Repl.java
private void processMessage(String input) {
    // 1. 保存到会话（第5/17章）
    ChatMessage userMsg = new ChatMessage("user", input);
    session.addMessage(userMsg);  // 同时追加到 JSONL 存档

    // 2. Hook: USER_PROMPT_SUBMIT（第21章）
    if (hookEngine != null) {
        HookContext ctx = HookContext.forUserPrompt(input);
        HookResult result = hookEngine.fire(HookEvent.USER_PROMPT_SUBMIT, ctx);
        if (result.intercept()) {
            console.printError("消息被拦截: " + result.message());
            return;
        }
        if (result.promptInject() != null) {
            input = result.promptInject();  // 替换用户输入
        }
    }

    // 3. 启动 AgentLoop（第9章）
    AgentLoop loop = new AgentLoop(
        provider, toolRegistry, permissionEngine, 
        new LoopConfig(25, 5, 3)  // maxIterations, maxParallelReads, consecutiveErrorLimit
    );

    // 4. 事件队列（第10章）
    BlockingQueue<AgentEvent> eventQueue = new LinkedBlockingQueue<>(1000);

    // 5. 后台线程运行 AgentLoop
    Thread agentThread = new Thread(() -> {
        try {
            loop.run(session.getHistory(), eventQueue);
        } catch (Exception e) {
            eventQueue.add(AgentEvent.error(e.getMessage()));
        }
    });
    agentThread.start();

    // 6. 主线程消费事件，渲染到终端
    consumeEvents(eventQueue);
}
```

**发生了什么：**

1. 用户消息保存到 session，同时追加写入 JSONL 文件
2. Hook 引擎检查 USER_PROMPT_SUBMIT 事件（假设没有匹配规则，放行）
3. 创建 AgentLoop，配置：最多 25 轮、最多 5 个并发读、连续 3 次错误退出
4. 创建事件队列（容量 1000）
5. 后台线程启动 AgentLoop，不阻塞主线程
6. 主线程调用 `consumeEvents()`，从队列取事件渲染

```
private ToolResult executeOne(ToolCall call) {
    // ── ① Hook: PRE_TOOL_USE（第21章）──
    if (hookEngine != null) {
        HookContext ctx = HookContext.forTool(call, null);
        HookResult result = hookEngine.fire(HookEvent.PRE_TOOL_USE, ctx);
        if (result.intercept()) {
            return ToolResult.error("HOOK_INTERCEPT: " + result.message());
        }
    }
    // 假设没有匹配的 Hook 规则 → 放行

    // ── ② 权限检查（第12/13章，五层串联）──
    PermissionResult perm = permissionEngine.check(call);
    if (!perm.allowed()) {
        return ToolResult.error("PERMISSION_DENIED: " + perm.reason());
    }

    // ── ③ 执行工具 ──
    Tool tool = toolRegistry.find(call.name());
    if (tool == null) {
        return ToolResult.error("工具不存在: " + call.name());
    }
    
    try {
        ToolResult result = tool.execute(call.input());
        eventQueue.put(AgentEvent.toolResult(call, result));
        return result;
    } catch (Exception e) {
        return ToolResult.error("工具执行失败: " + e.getMessage());
    }
}

**权限引擎五层检查（PermissionEngine.check）：**

```
// permission/PermissionEngine.java
public PermissionResult check(ToolCall call) {
    // 第1层：Blacklist（第12章）
    // 只对 exec_command 生效，edit_file 直接放行
    PermissionResult r1 = blacklist.check(call);
    if (!r1.allowed()) return r1;  // → 放行

    // 第2层：PathSandbox（第12章）
    // 检查 pom.xml 是否在项目目录内
    PermissionResult r2 = pathSandbox.check(call);
    if (!r2.allowed()) return r2;
    // pom.xml 在 /project/pom.xml，项目根是 /project
    // /project/pom.xml.startsWith(/project) → true → 放行

    // 第3层：RuleEngine（第13章）
    // 检查 .rook/rules.yaml 有没有匹配规则
    PermissionResult r3 = ruleEngine.check(call);
    if (!r3.allowed()) return r3;
    // 假设没有匹配规则 → 穿透

    // 第4层：PermissionMode（第13章）
    // edit_file 是 WRITE 类型
    // DEFAULT 模式: READ=ALLOW, WRITE=ASK, EXEC=ASK
    PermissionResult r4 = permissionMode.check(call);
    if (r4.allowed()) return r4;  // ALLOW 直接放行
    if (!r4.allowed() && r4.reason().equals("DENY")) return r4;  // DENY 直接拒绝
    // ASK → 进入第5层

    // 第5层：HumanInTheLoop（第13章）
    // 弹出终端确认
    return humanInTheLoop.ask(call);
}

// tools/impl/EditFileTool.java
public ToolResult execute(Map<String, Object> params) {
    String filePath = (String) params.get("file_path");
    String oldString = (String) params.get("old_string");
    String newString = (String) params.get("new_string");

    // 1. 读取文件
    Path path = Paths.get(filePath);
    String content = Files.readString(path);

    // 2. 统计匹配次数
    int count = 0;
    int idx = 0;
    while ((idx = content.indexOf(oldString, idx)) != -1) {
        count++;
        idx += oldString.length();
    }

    // 3. 必须恰好匹配 1 次
    if (count == 0) {
        return ToolResult.error("未找到匹配内容: " + oldString);
    }
    if (count > 1) {
        return ToolResult.error("匹配到 " + count + " 处，需要更精确的 old_string");
    }

    // 4. 替换
    String newContent = content.replace(oldString, newString);

    // 5. 原子写入（第7章：先写 .tmp，再 rename）
    Path tmpFile = path.resolveSibling(path.getFileName() + ".tmp");
    Files.writeString(tmpFile, newContent);
    Files.move(tmpFile, path, StandardCopyOption.ATOMIC_MOVE);

    return ToolResult.ok("已替换: " + oldString + " → " + newString);
}

**AutoMemory 异步做什么：**

- 把对话发给 LLM，让它提取有价值的记忆
- 比如："用户的项目 pom.xml 用 java.version 属性控制 Java 版本"
- 保存到～/.rook/memory/
- 不阻塞主流程，失败只记日志

### 第 5 步：consumeEvents — 事件渲染

```
// cli/Repl.java
private void consumeEvents(BlockingQueue<AgentEvent> queue) {
    while (true) {
        AgentEvent event = queue.poll(100, TimeUnit.MILLISECONDS);
        if (event == null) {
            // 超时，检查是否取消
            if (Thread.currentThread().isInterrupted()) break;
            continue;
        }

        switch (event.type()) {
            case TEXT:
                // 流式打印文本
                console.print(event.text());
                break;

            case TOOL_CALL:
                // 打印工具调用信息
                console.print("\n[调用工具: " + event.toolCall().name() + "]\n");
                console.print("  " + formatToolParams(event.toolCall()) + "\n");
                break;

            case TOOL_RESULT:
                if (event.toolResult().success()) {
                    console.printSuccess("[OK] " + event.toolResult().content());
                } else {
                    console.printError("[失败] " + event.toolResult().content());
                }
                break;

            case ERROR:
                console.printError("[错误] " + event.message());
                break;

            case DONE:
                console.print("\n");  // 补换行
                return;  // 退出消费循环
        }
    }
}
```

**终端渲染的完整过程：**

```
> 把 pom.xml 的 Java 版本从 11 改成 17
我来帮你修改 pom.xml 中的 Java 版本。
[调用工具: edit_file]
  文件: pom.xml
  替换: <java.version>11</java.version> → <java.version>17</java.version>
[OK] 已替换: <java.version>11</java.version> → <java.version>17</java.version>

已将 pom.xml 中的 Java 版本从 11 改为 17。

注意：我只修改了 <java.version>，但 pom.xml 中还有 
<maven.compiler.source> 和 <maven.compiler.target> 也是 11，
建议一起修改以保持一致。你可以运行 `mvn compile` 验证一下。

>
```

## 常见坑（走查中发现的）

### 1. 只改了 java.version，没改 compiler.source/target

**现象：** AI 只改了 `<java.version>`，但 `maven.compiler.source` 还是 11。

**原因：** AI 第一次调用 edit_file 只替换了一处，第二轮发现了但没主动改（等用户确认）。

**解决：**

- 好的 AI 会在第二轮主动提议一起改
- 或者用户说 "把所有 Java 版本相关的都改成 17"
- 这是 AI 理解的问题，不是框架的问题

### 2. 权限确认打断流式输出

**现象：** 文本输出到一半，弹出权限确认，用户体验不好。

**原因：** 工具调用在文本之后，权限确认在工具执行时。

**解决：**

- 这是正常的，先输出思考，再执行工具
- 可以优化：工具调用前先换行，再弹确认
- 或者批量确认（一次确认多个工具调用）

### 3. System Prompt 每次都重建

**现象：** 每轮都重新构建 System Prompt，浪费。

**原因：** 简单实现，每轮都 build。

**优化：**

- System Prompt 大部分是稳定的，可以缓存
- 只有上下文变化时才重建
- 配合 Anthropic prompt caching，缓存部分不收费

### 4. 事件队列 100ms 轮询

**现象：** consumeEvents 用 poll (100ms)，有 100ms 延迟。

**原因：** 为了能检测取消信号，不能用 take () 无限阻塞。

**解决：**

- 100ms 用户感觉不到
- 或者用 take () + 中断机制
- 当前实现是合理的折中

### 5. 异步记忆提取可能失败

**现象：** AutoMemory.updateAsync 失败了，用户不知道。

**原因：** 异步执行，失败只记日志。

**解决：**

- 记忆是锦上添花，失败不影响主流程
- 日志里有记录，排查时能看到
- 可以加个 /memory 命令查看提取状态
