# 15 — 上下文管理：防 Token 溢出

## 这一章做什么

实现**两层压缩策略**，防止对话历史太长撑爆 LLM 的 token 窗口。

- **第 1 层**：单条工具结果太大 → 存盘，对话里只留预览
- **第 2 层**：累积历史太长 → LLM 生成摘要，压缩旧消息

**完成后你能做到：**

- 读一个 50KB 的大文件？不会撑爆上下文，自动存盘只留预览
- 聊了 50 轮？不会超 128K 窗口，自动压缩旧消息
- 会话可以持续数小时，不会因为 token 溢出被 API 拒绝

## 为什么需要

### Token 窗口的限制

每个 LLM 都有 token 窗口上限：

- Claude 3.5 Sonnet：200K
- GPT-4o：128K
- DeepSeek V3：128K

**超过这个限制，API 直接返回 400 错误。**

### Agent Loop 的问题

我们的 Agent Loop 每轮都往 history 里追加消息：

```
第 1 轮：user + assistant + tool_result
第 2 轮：user + assistant + tool_result
第 3 轮：...
...
第 10 轮：已经有 30+ 条消息了
```

**如果工具返回的内容很大，问题更严重：**

- 读一个 50KB 的文件 → 一条消息就 1 万多 token
- grep 一个大项目 → 返回几千行匹配结果
- exec_command 输出日志 → 可能几 MB

**10 轮对话轻松超 128K。**

### 两层压缩的思路

```
┌─────────────────────────────────────────────────┐
│ 第 1 层：单条消息太大 → 存盘，只留预览            │
│   针对：单个工具结果特别大                        │
│   效果：一条 50KB 的消息变成 200 字节预览          │
└────────────────────┬────────────────────────────┘
                     │
                     ▼
┌─────────────────────────────────────────────────┐
│ 第 2 层：累积历史太长 → LLM 生成摘要              │
│   针对：消息太多，加起来还是超窗口                 │
│   效果：50 轮旧消息压缩成一段 1K 的摘要            │
└─────────────────────────────────────────────────┘
```

**两层配合，会话可以持续很久。**

## 核心概念

### 第 1 层：单条结果存盘

- 阈值：单条工具结果 > 8KB
- 动作：写入 `~/.rook/context/` 目录
- 对话中替换为：预览（前 200 字符）+ 文件路径
- 好处：大内容不占上下文，需要时可以从文件读

### 第 2 层：历史摘要压缩

- 阈值：总 token > 窗口 - 13K（留 13K 余量）
- 动作：把旧消息发给 LLM，生成结构化摘要
- 保留：最近～10K token 的原文
- 好处：旧消息压缩成摘要，腾出空间

### TokenEstimator

估算当前历史的 token 数：

- 锚定最近一次 API 返回的 usage（精确）
- 新增消息用 字符数 / 4 估算
- 英文准（1 token ≈ 4 字符），中文偏大（1 token ≈ 1-2 字符）

## 第一步：ToolResultStorage — 第 1 层存盘

单条工具结果太大时，存盘只留预览。

```
// context/ToolResultStorage.java
package com.rook.context;

import com.rook.tools.ToolCall;
import com.rook.tools.ToolResult;
import java.io.IOException;
import java.nio.file.*;
import java.time.LocalDateTime;
import java.time.format.DateTimeFormatter;

public class ToolResultStorage {

    private final Path contextDir;
    private final int threshold;  // 超过这个大小就存盘，默认 8192 (8KB)

    public ToolResultStorage(Path contextDir, int threshold) {
        this.contextDir = contextDir;
        this.threshold = threshold;
    }

    public ToolResultStorage(Path contextDir) {
        this(contextDir, 8192);  // 默认 8KB
    }

    /**
     * 如果工具结果太大，存盘并返回预览版
     * @return 原始内容（小）或预览内容（大）
     */
    public String maybeStore(ToolCall call, ToolResult result) {
        String content = result.content();
        
        // 没超过阈值，直接返回原文
        if (content.length() < threshold) {
            return content;
        }

        try {
            // 确保目录存在
            Files.createDirectories(contextDir);

            // 生成文件名：时间戳 + 工具名
            String timestamp = LocalDateTime.now()
                .format(DateTimeFormatter.ofPattern("yyyyMMdd_HHmmss_SSS"));
            String fileName = timestamp + "_" + sanitize(call.name()) + ".txt";
            Path file = contextDir.resolve(fileName);

            // 存盘
            Files.writeString(file, content);

            // 生成预览：前 200 字符
            String preview = content.substring(0, Math.min(200, content.length()));
            
            // 返回替换文本
            return "[工具结果已存盘]\n"
                + "  文件: " + file + "\n"
                + "  大小: " + content.length() + " 字节\n"
                + "  预览: " + preview + "...\n"
                + "  如需完整内容，请使用 read_file 工具读取该文件";

        } catch (IOException e) {
            // 存盘失败，返回原文（降级）
            System.err.println("[Context] 存盘失败: " + e.getMessage());
            return content;
        }
    }

    /**
     * 清理文件名中的非法字符
     */
    private String sanitize(String name) {
        return name.replaceAll("[^a-zA-Z0-9_-]", "_");
    }
}
```

### 逐段详解

#### 1. 阈值判断

```
if (content.length() < threshold) {
    return content;
}
```

没超过阈值（默认 8KB），直接返回原文，不处理。

**为什么是 8KB？**

- 8KB 大约 2000 token（英文），不算大
- 超过 8KB 的结果，通常是大文件、长日志
- 存盘只留预览，能省很多 token

**阈值可以调：**

- 想省 token → 设小一点，比如 4KB
- 想保留更多上下文 → 设大一点，比如 16KB

#### 2. 生成文件名

```
String timestamp = LocalDateTime.now()
    .format(DateTimeFormatter.ofPattern("yyyyMMdd_HHmmss_SSS"));
String fileName = timestamp + "_" + sanitize(call.name()) + ".txt";
```

文件名包含时间戳和工具名，方便查找：

- `20260813_153045_123_read_file.txt`
- `20260813_153100_456_grep.txt`

**毫秒级时间戳**，避免同名冲突。

#### 3. 存盘

```
Files.writeString(file, content);
```

把完整内容写入文件。

#### 4. 生成预览

```
String preview = content.substring(0, Math.min(200, content.length()));

return "[工具结果已存盘]\n"
    + "  文件: " + file + "\n"
    + "  大小: " + content.length() + " 字节\n"
    + "  预览: " + preview + "...\n"
    + "  如需完整内容，请使用 read_file 工具读取该文件";
```

**替换文本包含：**

- 文件路径（AI 需要的话可以自己读）
- 大小（让 AI 知道有多大）
- 前 200 字符预览（让 AI 大概知道内容是什么）
- 提示（告诉 AI 怎么获取完整内容）

**50KB 的内容，变成 300 字节的预览，省了 99% 的 token。**

#### 5. 降级处理

```
} catch (IOException e) {
    System.err.println("[Context] 存盘失败: " + e.getMessage());
    return content;  // 返回原文
}
```

存盘失败了怎么办？

- 不能因为存盘失败就丢了结果
- 降级：返回原文，虽然占 token 但至少不丢数据

## 第二步：TokenEstimator — Token 估算

估算当前历史的 token 数。

```
// context/TokenEstimator.java
package com.rook.context;

import com.rook.llm.ChatMessage;
import java.util.List;

public class TokenEstimator {

    private long lastKnownTokens = 0;  // 最近一次 API 返回的精确 token 数
    private int lastMessageCount = 0;  // 上次估算时的消息数

    /**
     * 更新精确 token 数（API 返回 usage 时调用）
     */
    public void updateFromUsage(int promptTokens, int messageCount) {
        this.lastKnownTokens = promptTokens;
        this.lastMessageCount = messageCount;
    }

    /**
     * 估算当前历史的 token 数
     */
    public long estimate(List<ChatMessage> messages) {
        if (messages.isEmpty()) {
            return 0;
        }

        // 如果消息数没变，直接用上次的精确值
        if (messages.size() == lastMessageCount) {
            return lastKnownTokens;
        }

        // 估算新增消息的 token
        long estimated = lastKnownTokens;
        for (int i = lastMessageCount; i < messages.size(); i++) {
            estimated += estimateOne(messages.get(i));
        }
        return estimated;
    }

    /**
     * 估算单条消息的 token 数
     * 简单估算：字符数 / 4
     * 英文准，中文偏大（保守估计）
     */
    private long estimateOne(ChatMessage message) {
        String content = message.content();
        if (content == null) {
            content = "";
        }
        // 字符数 / 4，加 10 个固定开销（角色名、格式等）
        return content.length() / 4 + 10;
    }

    /**
     * 找到分割点：尾部保留 targetTokens 的原文，前面的压缩
     */
    public int findSplitPoint(List<ChatMessage> messages, int targetTokens) {
        long count = 0;
        // 从后往前数，直到超过 targetTokens
        for (int i = messages.size() - 1; i >= 0; i--) {
            count += estimateOne(messages.get(i));
            if (count >= targetTokens) {
                return i;  // 从 i 开始保留
            }
        }
        return 0;  // 全部保留
    }

    public void reset() {
        lastKnownTokens = 0;
        lastMessageCount = 0;
    }
}
```

### 逐段详解

#### 1. 为什么需要估算？

每次调 API 都能拿到精确的 usage，但：

- 我们要在调 API **之前**判断要不要压缩
- 这时候还没有 usage，只能估算

#### 2. 锚定 + 增量估算

```
// 精确值（上次 API 返回的）
private long lastKnownTokens = 0;

// 估算新增的
for (int i = lastMessageCount; i < messages.size(); i++) {
    estimated += estimateOne(messages.get(i));
}
```

**思路：**

- 上次调 API 拿到了精确 token 数 → 作为锚点
- 之后新增的消息，用 字符数 / 4 估算
- 加起来就是当前估算值

**比纯估算准很多：**

- 纯估算：每条都 字符数 / 4，误差累积
- 锚定 + 增量：只有新增的有误差，旧的是精确的

#### 3. 字符数 / 4 估算

```
private long estimateOne(ChatMessage message) {
    String content = message.content();
    return content.length() / 4 + 10;
}
```

**为什么是 /4？**

- 英文：1 token ≈ 4 字符 → 准
- 中文：1 token ≈ 1-2 字符 → /4 会偏小（估少了）

**中文的问题：**

- 比如 "你好世界" 4 个字符，/4 = 1 token
- 实际可能是 2-4 token
- 估算值比实际小，可能导致超窗口

**怎么解决？**

- 多留余量（13K）
- 或者对中文用 /2 估算
- 或者统计中英文比例，加权估算

我们用的是 "多留余量" 的方案，简单有效。

#### 4. findSplitPoint — 找分割点

```
public int findSplitPoint(List<ChatMessage> messages, int targetTokens) {
    long count = 0;
    for (int i = messages.size() - 1; i >= 0; i--) {
        count += estimateOne(messages.get(i));
        if (count >= targetTokens) {
            return i;
        }
    }
    return 0;
}
```

**从后往前数，保留最近 targetTokens 的原文。**

比如 targetTokens = 10000：

- 从最后一条消息开始往前数
- 数到累计 10000 token 了，就从这里分割
- 前面的压缩，后面的保留原文

**为什么保留最近的？**

- 最近的消息和当前任务最相关
- 越旧的消息越不重要，可以压缩

## 第三步：ContextSummarizer — 第 2 层摘要压缩

历史太长时，用 LLM 生成摘要，压缩旧消息。

```
// context/ContextSummarizer.java
package com.rook.context;

import com.rook.llm.ChatMessage;
import com.rook.llm.LlmProvider;
import java.util.ArrayList;
import java.util.List;

public class ContextSummarizer {

    private final TokenEstimator estimator;
    private int consecutiveFailures = 0;
    private static final int MAX_FAILURES = 3;  // 连续失败 3 次熔断

    public ContextSummarizer(TokenEstimator estimator) {
        this.estimator = estimator;
    }

    /**
     * 压缩历史：旧消息生成摘要，保留最近的原文
     */
    public List<ChatMessage> summarize(List<ChatMessage> messages, LlmProvider provider) {
        // 熔断：连续失败太多次，不压缩了
        if (consecutiveFailures >= MAX_FAILURES) {
            System.err.println("[Context] 摘要连续失败，已熔断，跳过压缩");
            return messages;
        }

        // 找分割点：尾部保留 ~10K token
        int split = estimator.findSplitPoint(messages, 10000);
        
        if (split <= 0) {
            return messages;  // 不需要压缩
        }

        List<ChatMessage> toSummarize = messages.subList(0, split);
        List<ChatMessage> toKeep = messages.subList(split, messages.size());

        try {
            // 调 LLM 生成摘要
            String summary = generateSummary(toSummarize, provider);
            
            // 组装新的历史
            List<ChatMessage> result = new ArrayList<>();
            
            // 1. 摘要消息
            result.add(new ChatMessage("user", 
                "## 历史对话摘要\n" + summary + "\n\n"
                + "（以上是较早对话的摘要，可能不完整。"
                + "不要根据摘要脑补具体代码细节，需要时用工具重新读取。）"));
            
            // 2. 边界消息（标记压缩位置）
            result.add(new ChatMessage("user", 
                "--- 以下是最近的对话原文 ---"));
            
            // 3. 保留的原文
            result.addAll(toKeep);

            consecutiveFailures = 0;  // 成功，重置失败计数
            return result;

        } catch (Exception e) {
            consecutiveFailures++;
            System.err.println("[Context] 摘要生成失败: " + e.getMessage());
            return messages;  // 失败，返回原文（降级）
        }
    }

    /**
     * 调 LLM 生成摘要
     */
    private String generateSummary(List<ChatMessage> messages, LlmProvider provider) 
            throws Exception {
        // 构建摘要 prompt
        String prompt = buildSummaryPrompt(messages);
        
        // 调 LLM（不带工具，纯文本生成）
        // complete 方法是非流式的，直接返回完整结果
        return provider.complete(List.of(
            new ChatMessage("user", prompt)
        ));
    }

    /**
     * 构建摘要 prompt
     */
    private String buildSummaryPrompt(List<ChatMessage> messages) {
        StringBuilder sb = new StringBuilder();
        sb.append("请对以下对话历史生成结构化摘要。\n\n");
        sb.append("要求：\n");
        sb.append("1. 保留关键决策和结论\n");
        sb.append("2. 保留已完成的步骤和结果\n");
        sb.append("3. 保留重要的文件路径和命令\n");
        sb.append("4. 不要保留具体的代码内容（只说"修改了 X 文件"）\n");
        sb.append("5. 简洁，控制在 500 字以内\n\n");
        sb.append("对话历史：\n");
        sb.append("---\n");
        
        for (ChatMessage msg : messages) {
            sb.append("[").append(msg.role()).append("]\n");
            sb.append(msg.content()).append("\n\n");
        }
        
        sb.append("---\n\n");
        sb.append("请生成摘要：");
        
        return sb.toString();
    }

    public void reset() {
        consecutiveFailures = 0;
    }
}
```

### 逐段详解

#### 1. 熔断机制

```
if (consecutiveFailures >= MAX_FAILURES) {
    System.err.println("[Context] 摘要连续失败，已熔断，跳过压缩");
    return messages;
}
```

**为什么需要熔断？**

- 摘要生成要调 LLM，可能失败（网络、超时、API 错误）
- 如果每次都失败，每次都重试，浪费时间和钱
- 连续失败 3 次，就熔断，不再尝试压缩

**熔断后怎么办？**

- 不压缩了，直接用原文
- 虽然可能超窗口，但至少不阻塞主流程
- 可以手动重置，或者下次会话重置

#### 2. 找分割点

```
int split = estimator.findSplitPoint(messages, 10000);
```

保留最近 10000 token 的原文，前面的压缩。

**为什么是 10K？**

- 最近的消息最相关，保留原文
- 10K 大约够 5-10 轮对话
- 太旧的消息压缩成摘要就行

#### 3. 生成摘要

```
private String generateSummary(List<ChatMessage> messages, LlmProvider provider) {
    String prompt = buildSummaryPrompt(messages);
    return provider.complete(List.of(
        new ChatMessage("user", prompt)
    ));
}
```

**调 LLM 生成摘要，注意：**

- 不带工具（纯文本生成）
- 用 complete 方法（非流式）
- 把要压缩的消息都放进 prompt

#### 4. 摘要 prompt

```
private String buildSummaryPrompt(List<ChatMessage> messages) {
    StringBuilder sb = new StringBuilder();
    sb.append("请对以下对话历史生成结构化摘要。\n\n");
    sb.append("要求：\n");
    sb.append("1. 保留关键决策和结论\n");
    sb.append("2. 保留已完成的步骤和结果\n");
    sb.append("3. 保留重要的文件路径和命令\n");
    sb.append("4. 不要保留具体的代码内容（只说"修改了 X 文件"）\n");
    sb.append("5. 简洁，控制在 500 字以内\n\n");
    ...
}
```

**摘要的要求很重要：**

- 保留什么：决策、结论、步骤、文件路径、命令
- 不保留什么：具体代码内容（太占 token）
- 长度：500 字以内

**为什么不保留具体代码？**

- 代码占 token 多
- AI 需要的话可以重新读文件
- 摘要里只说 "修改了 pom.xml，把 Java 版本改成 21" 就行

#### 5. 组装新历史

```
List<ChatMessage> result = new ArrayList<>();

// 1. 摘要消息
result.add(new ChatMessage("user", 
    "## 历史对话摘要\n" + summary + "\n\n"
    + "（以上是较早对话的摘要，可能不完整。"
    + "不要根据摘要脑补具体代码细节，需要时用工具重新读取。）"));

// 2. 边界消息
result.add(new ChatMessage("user", 
    "--- 以下是最近的对话原文 ---"));

// 3. 保留的原文
result.addAll(toKeep);
```

**新历史的结构：**

```
[摘要消息]  历史摘要 + 警告（不要脑补）
[边界消息]  --- 以下是最近的对话原文 ---
[原文 1]
[原文 2]
...
```

**警告很重要：**

"不要根据摘要脑补具体代码细节，需要时用工具重新读取。"

因为摘要可能不完整，如果 AI 根据摘要脑补代码，会出错。

明确告诉它：摘要只是参考，具体内容要重新读。

#### 6. 失败降级

```
} catch (Exception e) {
    consecutiveFailures++;
    System.err.println("[Context] 摘要生成失败: " + e.getMessage());
    return messages;  // 返回原文
}
```

摘要生成失败了怎么办？

- 不能因为摘要失败就整个任务崩了
- 降级：返回原文，不压缩
- 虽然可能超窗口，但至少不丢数据

## 第四步：ContextManager — 统一管理

把两层压缩封装在一起，提供统一接口。

```
// context/ContextManager.java
package com.rook.context;

import com.rook.llm.ChatMessage;
import com.rook.llm.LlmProvider;
import com.rook.tools.ToolCall;
import com.rook.tools.ToolResult;
import java.util.List;

public class ContextManager {

    private final ToolResultStorage storage;
    private final ContextSummarizer summarizer;
    private final TokenEstimator estimator;
    private final int contextWindow;  // 模型的 token 窗口大小

    public ContextManager(
            ToolResultStorage storage,
            ContextSummarizer summarizer,
            TokenEstimator estimator,
            int contextWindow) {
        this.storage = storage;
        this.summarizer = summarizer;
        this.estimator = estimator;
        this.contextWindow = contextWindow;
    }

    /**
     * 第 1 层：处理工具结果，太大就存盘
     */
    public String processToolResult(ToolCall call, ToolResult result) {
        return storage.maybeStore(call, result);
    }

    /**
     * 第 2 层：如果历史太长，压缩
     * @param force 是否强制压缩（用户手动触发）
     */
    public List<ChatMessage> prepare(
            List<ChatMessage> history,
            LlmProvider provider,
            boolean force) {
        
        long estimated = estimator.estimate(history);
        long threshold = contextWindow - 13000;  // 留 13K 余量

        if (force || estimated > threshold) {
            System.out.println("[Context] 触发压缩，当前估算: " 
                + estimated + " token，阈值: " + threshold);
            return summarizer.summarize(history, provider);
        }

        return history;
    }

    /**
     * 更新 token 估算（API 返回 usage 时调用）
     */
    public void updateTokenUsage(int promptTokens, int messageCount) {
        estimator.updateFromUsage(promptTokens, messageCount);
    }

    /**
     * 获取当前状态（用于 :compress status 命令）
     */
    public String status(List<ChatMessage> history) {
        long estimated = estimator.estimate(history);
        return String.format(
            "Token 估算: %d / %d (阈值: %d)\n"
            + "余量: %d\n"
            + "消息数: %d",
            estimated,
            contextWindow,
            contextWindow - 13000,
            contextWindow - estimated,
            history.size()
        );
    }
}
```

### 逐段详解

#### 1. prepare — 压缩入口

```
public List<ChatMessage> prepare(
        List<ChatMessage> history,
        LlmProvider provider,
        boolean force) {
    
    long estimated = estimator.estimate(history);
    long threshold = contextWindow - 13000;

    if (force || estimated > threshold) {
        return summarizer.summarize(history, provider);

    return history;
```

**什么时候压缩？**

- 自动：估算 token > 窗口 - 13K
- 手动：用户输入 `:compress` 命令，force=true

**为什么留 13K 余量？**

- 估算不准（中文偏大）
- 下一轮还要加新消息
- LLM 生成回复也要 token
- 留 13K，安全

## 第五步：AgentLoop 集成

把上下文管理集成到 Agent Loop 里。

```
// core/agent/AgentLoop.java（片段）

public void run() {
    while (state == LoopState.RUNNING) {
        iteration++;
        
        // ★ 每轮 LLM 调用前，检查是否需要压缩
        history = contextManager.prepare(history, provider, false);
        
        // 调 LLM
        StreamCollector collector = new StreamCollector(...);
        provider.stream(history, tools, collector);
        
        // ★ 更新 token 估算（从 collector 拿 usage）
        contextManager.updateTokenUsage(
            collector.getPromptTokens(), 
            history.size()
        );
        
        String text = collector.getFullText();
        List<ToolCall> toolCalls = collector.getToolCalls();
        
        if (toolCalls.isEmpty()) {
            state = COMPLETED;
            break;
        }
        
        // 执行工具
        List<ToolResult> results = executor.execute(toolCalls);
        
        // ★ 第 1 层：处理工具结果，太大就存盘
        List<String> processedResults = new ArrayList<>();
        for (int i = 0; i < toolCalls.size(); i++) {
            processedResults.add(
                contextManager.processToolResult(toolCalls.get(i), results.get(i))
            );
        }
        
        // 回灌结果
        history.add(new ChatMessage("assistant", text, toolCalls));
        history.add(new ChatMessage("user", buildToolResultContent(processedResults)));
    }
}
```

### 三个集成点

#### 1. LLM 调用前：检查压缩

```
history = contextManager.prepare(history, provider, false);
```

每轮调 LLM 之前，检查历史是不是太长了，太长就压缩。

#### 2. LLM 调用后：更新 token 估算

```
contextManager.updateTokenUsage(
    collector.getPromptTokens(), 
    history.size()
);
```

API 返回了精确的 usage，更新估算器的锚点。

#### 3. 工具执行后：处理大结果

```
for (int i = 0; i < toolCalls.size(); i++) {
    processedResults.add(
        contextManager.processToolResult(toolCalls.get(i), results.get(i))
    );
}
```

工具结果太大的话，存盘只留预览。

## 常见坑（详细版）

### 1. 字符 / 4 估算不准

**现象：** 估算没超阈值，但 API 还是返回 400（token 超限）。

**原因：** 中文 token 密度高，字符数 / 4 估少了。

| 语言 | 1 token ≈ 字符数 | 字符数 / 4 估算 |
| :--: | :--------------: | :-------------: |
| 英文 |        4         |       准        |
| 中文 |       1-2        | 偏小（估少了）  |
| 代码 |       3-4        |      较准       |

**解决：**

- 多留余量（我们留了 13K）
- 或者对中文用 /2 估算
- 或者检测中英文比例，加权估算
- 最简单：余量留大一点，宁可提前压缩

### 2. 摘要 LLM 失败

**现象：** 摘要生成失败，或者超时。

**原因：**

- 网络问题
- API 限流
- 要压缩的消息本身就超窗口了（悖论：要压缩，但压缩用的 prompt 也超了）

**解决：**

- 熔断：连续失败 3 次就不压缩了
- 降级：失败就返回原文，不阻塞主流程
- 分批压缩：如果要压缩的内容太多，分多次压缩
- 用更便宜的模型生成摘要（比如 Haiku）

### 3. 边界消息和 "不要脑补" 警告

**现象：** 压缩后，AI 根据摘要脑补代码细节，改错了。

**原因：** 摘要不完整，但 AI 以为摘要就是全部，自己脑补缺失的部分。

**解决：**

- 摘要消息里明确警告："不要根据摘要脑补具体代码细节，需要时用工具重新读取"
- 边界消息标记："--- 以下是最近的对话原文 ---"
- 让 AI 清楚区分：哪些是摘要（可能不完整），哪些是原文（准确）

**这条警告很关键，不能省。**

### 4. 存盘文件越来越多

**现象：** `~/.rook/context/` 目录下文件越来越多，占磁盘。

**原因：** 每次大结果都存盘，不清理。

**解决：**

- 定期清理：启动时删除 N 天前的文件
- 或者按大小清理：超过一定大小就删最旧的
- 或者会话结束时清理：当前会话的存盘文件，会话结束就删
- 提供 `:compress clean` 命令手动清理

### 5. 压缩后工具结果引用失效

**现象：** 压缩前的工具结果存盘了，压缩后 AI 想读那个文件，但路径在摘要里可能丢了。

**原因：** 摘要可能没保留存盘文件的路径。

**解决：**

- 摘要 prompt 里要求："保留重要的文件路径和命令"
- 或者存盘文件的路径单独记录，不进摘要
- 或者 AI 需要的话，可以重新执行工具

### 6. 多次压缩的累积误差

**现象：** 压缩了好几次后，摘要越来越模糊，关键信息丢了。

**原因：** 每次压缩都是 "摘要的摘要"，信息损失累积。

**解决：**

- 压缩时，把之前的摘要也放进 prompt，让 LLM 整合
- 或者限制压缩次数，最多压缩 N 次
- 或者重要信息单独存储（比如项目笔记），不依赖摘要

### 7. 摘要 prompt 本身超窗口

**现象：** 要压缩的消息太多，连摘要 prompt 都超窗口了。

**原因：** 触发压缩的阈值太晚，历史已经非常长了。

**解决：**

- 阈值设早一点（比如窗口的 70% 就触发）
- 或者分批压缩：先压缩前一半，再压缩后一半
- 或者用更激进的第 1 层（更小的阈值，更多内容存盘）

### 8. 多轮对话中的 system prompt

**现象：** 压缩时把 system prompt 也压缩了，导致行为异常。

**原因：** system prompt 在 messages [0]，压缩时可能被当成普通消息压缩掉。

**解决：**

- 压缩时跳过 system prompt（messages [0]）
- 或者 system prompt 单独管理，不进 history
- 我们的实现里，system prompt 是单独传的，不在 history 里，所以没问题

## 两层压缩总结

|  层级   |       触发条件        |      动作      |        效果        |
| :-----: | :-------------------: | :------------: | :----------------: |
| 第 1 层 |    单条结果 > 8KB     | 存盘，只留预览 |  50KB → 300 字节   |
| 第 2 层 | 总 token > 窗口 - 13K |  LLM 生成摘要  | 50 轮 → 500 字摘要 |

**第 1 层针对 "单个大结果"，第 2 层针对 "累积历史太长"。**

两层配合，会话可以持续数小时不溢出。
