# MewCode 第4章 - 结构化 System Prompt Spec

## 背景

ch01-ch03 搭建了对话、工具、Agent Loop 三大能力。但系统提示（System Prompt）
始终是硬编码的一行字符串，注入逻辑散落在 Repl 中。

现状问题：
- 所有指令塞在一段文本里，增/删/改规则靠字符串拼接，容易出错
- 没有区分"稳定内容"和"变化内容"——稳定指令本可被 LLM API 缓存，
  变化部分（环境信息、会话状态）每次都在变，导致缓存失效、token 浪费
- Plan Mode 的系统提示靠 `contains("计划模式")` 字符串匹配来增删，脆弱
- 工具描述里的关键规则和全局指令里的规则没有相互呼应

## 目标

- 把全局指令拆成按职责划分的若干模块，按优先级拼装成完整系统提示；新增一类指令只需挂载新模块，不改装配逻辑
- 区分稳定与变化内容：稳定的系统模块与工具定义走可缓存通道；环境信息与对话历史走不缓存的通道
- 在工具描述与系统提示中，对关键约定（优先用专用工具、编辑前必先读）双重强化，提高遵守率
- 提供一种带特殊标签的补充消息注入机制：运行中注入补充指令，既不污染缓存，也不会被模型当成用户输入来回复
- 会话级开关（规划模式）的提醒按轮次注入：首轮完整、间隔轮次重复完整、其余轮次精简，控制注入频率
- 能从 provider 返回中解析缓存命中信息（写入/读取 token），用于验证缓存策略真实生效

## 功能需求

### 模块化 Prompt 构建
- F1: 定义 `PromptModule` 抽象 —— 每个模块有名称、优先级、内容生成方法
- F2: 七个固定模块，按优先级从高到低排列：

| 优先级 | 模块 | 职责 |
|--------|------|------|
| 1 | 身份 | Agent 名称、版本、角色定位 |
| 2 | 系统约束 | 硬性规则（不编造、不跳过流程、错误处理） |
| 3 | 任务模式 | 当前工作模式（正常/Plan Mode）及对应行为 |
| 4 | 动作执行 | 工具调用后的处理流程（结果回灌、多轮判断） |
| 5 | 工具使用 | 通用工具约定 + 关键规则双重强化（优先专用工具、编辑前必读） |
| 6 | 语气风格 | 语言、详略、交互习惯 |
| 7 | 文本输出 | 输出格式约束、代码块规范 |

- F3: 三个可选模块（排在固定模块之后）：

| 模块 | 职责 |
|------|------|
| 自定义指令 | 用户/项目补充规则 |
| 已激活 Skill | 当前会话启用的技能描述 |
| 长期记忆 | 历史交互中沉淀的关键信息 |

- F4: 模块间空行分隔，整体按优先级从前往后拼装
- F5: `PromptBuilder` 作为装配器：接收模块列表，按优先级排序后拼接输出最终 System Prompt 文本

### 缓存感知
- F6: 稳定内容（七个固定模块 + 工具描述）以 `system` 角色注在 messages[0] 位置，走 Anthropic 的 prompt caching
- F7: 变化内容（环境信息如当前目录、操作系统、日期时间等）以独立 system 消息或 user 消息注入，不走缓存
- F8: 从 Provider SSE 响应中解析 `cache_read_input_tokens` / `cache_creation_input_tokens` 字段（Anthropic 格式），记录为 Usage 的一部分

### 补充消息注入
- F9: 定义特殊的消息角色标记 `[Supplement]`，运行时补充指令以该标记包装注入
- F10: 补充消息不影响缓存结构（不在 system 位置），不被模型当作用户输入来回复
- F11: Plan Mode 的会话级开关指令通过补充消息机制注入

### 注入频率控制
- F12: 会话级开关（Plan Mode）指令按轮次策略注入：
  - 首轮（iteration=1）：注入完整提示
  - 间隔轮次（每 N 轮，默认 N=3）：重新注入完整提示
  - 其余轮次：注入精简版（一行提示）

### 双重强化
- F13: 关键规则同时在 `工具使用` 模块和 `工具描述` 中体现：
  - "优先使用专用工具，不要手工模拟工具操作"
  - "编辑文件前必须先读取文件内容"
- F14: 工具描述中附加 `[重要]` 标记强调关键规则

### 缓存命中验证
- F15: 扩展 Usage record 增加 `cacheReadInputTokens` / `cacheCreationInputTokens` 字段
- F16: 从 AnthropicProvider SSE 流中解析 `message_start` 事件里的 usage 字段获取缓存信息
- F17: AgentLoop 中记录每轮的缓存命中情况，通过 TOKEN_USAGE 事件推送

## 非功能需求

- N1: **模块化不降性能** — PromptBuilder 拼装耗时 < 10ms，不影响首 token 时延
- N2: **向后兼容** — 现有 Provider 不加 Prompt 时行为不变
- N3: **模块可插拔** — 新增一个 PromptModule 只需新建一个类并注册，不改 Builder 逻辑
- N4: **缓存信息不影响正常流** — 解析不到缓存字段时不报错，Usage 字段默认为 0

## 不做的事（本章明确排除）

- 从 CLAUDE.md / 项目文件自动加载指令
- 自动记忆功能
- 真实 MCP 协议接入
- 自动化评估 / A/B 测试系统
- Prompt 版本管理与回滚

## 验收标准

### 模块化构建
- AC1: PromptBuilder 接收七个固定模块 + 可选模块，输出字符串含所有模块且按优先级排列
- AC2: 新增一个自定义模块并注册，PromptBuilder 自动在正确位置插入，不改 Builder 代码

### 缓存感知
- AC3: 稳定模块以 system 角色注入 messages[0]，环境信息以独立 system 消息注入 messages 末尾
- AC4: Usage record 包含 cacheReadInputTokens 和 cacheCreationInputTokens 字段
- AC5: 调用 Anthropic API 后，lastUsage() 中缓存字段非负（≥0）

### 补充消息注入
- AC6: 以 `[Supplement]` 标记的补充消息注入后，程序不将其视为用户轮次
- AC7: Plan Mode 切换后在消息历史中可见 `[Supplement]` 标记的上下文注入

### 注入频率控制
- AC8: Plan Mode 下首轮消息包含完整提示，第4轮（间隔3）重现完整提示，第2-3轮为精简版
- AC9: 非 Plan Mode 下不注入任何模式相关提示

### 双重强化
- AC10: 工具的 description 中包含"编辑前先读"等关键规则
- AC11: System Prompt 的"工具使用"模块中包含相同的规则

### 缓存命中验证
- AC12: 单元测试验证 Anthropic 格式的 cache_read_input_tokens 可被正确解析
- AC13: 多轮对话后，TOKEN_USAGE 事件中的缓读写/读取 token 数字合理增长
